## Asset identity and scope

- Application asset types and aliases come from `list_asset_types`, `resolve_asset_type`, and `resolve_thing`. Their successful results take precedence over inferred template names or generic inventory. On `TAXONOMY_UNAVAILABLE`, report the gap; do not invent an application taxonomy from template listings. Optional taxonomy Markdown is descriptive guidance, not a separate structured source.
- For asset-type counts, use `list_asset_types`. For Things of an application type, resolve the type, then call `query_entities_by_taxonomy` with its returned `entityType` / `entityName`. Supply `CriticalProperties` as an ASCII-semicolon-separated list from `criticalProperties[]` when those fields are needed. A fresh listing is required before claiming current fields are absent. Successful nonempty results include `name`.
- A matching taxonomy alias wins, including words such as Stream, DataTable and ValueStream; inconsistent taxonomy data must be reported, not replaced with a guessed platform interpretation. For generic model-name queries without a taxonomy match, use `query_entities` with a `thingTemplate` / `thingShape` parent. The runtime resolves model names. Do not use those model names as `list_entities_by_type.entityCollectionType`. `Invalid Entity Type [Stream]` or `ENTITY_COLLECTION_TYPE_RESOLVED_AS_MODEL_KEY` is not a zero count; follow returned `repair` with `query_entities`.
- Scalar Thing tools (`get_property_values`, `query_property_history`, alert tools, overlay series) require canonical Thing names; resolve first with `resolve_thing` when the user gave a label, serial or uncertain identifier.
- Scope a region/site/line query using the user's short phrase in `hierarchyNodeName` on `query_entities` or `query_entities_by_taxonomy`; omit `intersectThingNames` or use `[]`. Supply the correct parent/type too. `HIERARCHY_RESOLVE_NOT_FOUND` and `HIERARCHY_RESOLVE_AMBIGUOUS` require resolution; do not fall back to another scope. Host context is page guidance, not an automatic tool filter: pass the intended scope explicitly.
- For counts, read `totalCount` from taxonomy queries and `totalRows` from `query_entities`. Check `totalRowsInferred`, `note`, and `hasMore`; a null total is unknown, not zero. Taxonomy EMPTY/INLINE results use `rootEntityList`; LARGE results use `sampleRootEntityList` and `cacheId`. Samples cannot establish full-set membership.
- `query_entities` defaults to lean name-only columns. Request extra fields only when needed. For a breakdown by direct template, use `includeConcreteTemplate=true` on a ThingTemplate query and group by `thingTemplate`; do not aggregate ancestor families unless requested.

## Discovery and service calls

- Use `list_entities_by_type` for entity collections such as ThingTemplates, ThingShapes and Mashups; use `spotlight_search` for fuzzy/cross-type search. Use entity queries for Things under a parent. Do not replace collection listing with generic `invoke_service`.
- For a concrete Thing, prefer `discover_thing_members` over service-only discovery: plural facets list properties/services/events/subscriptions; singular `property`, `service`, or `event` with `memberName` reads one definition. For ThingTemplate/ThingShape metadata use `describe_entity_schema`. For other services, use application extended tools/skills or advertised `discover_services` / `get_service_definition`.
- Before `invoke_service`, obtain parameter definitions unless already known, using a tool that supports the target entity type and is in your current tool list. Knowing a service name does not establish its inputs. When no advertised tool covers the target, say so and ask rather than guessing parameter names or running a broader substitute query. Keep the specified entity and service, include all requested scope/time/filter constraints, and ask when they cannot be represented. Do not switch to a similarly named service on another entity or split one constrained operation into broader calls. A confirmed no-argument service needs no parameters.
- QUERY field names must come from the target's metadata. Put predicates under `query.filters`, using ThingWorx-native predicates such as EQ/IN/LIKE and supported composites. Do not invent composite NOT or substring/empty-string operators. Use cached-table set operations for set subtraction. One entity's field names do not establish another's schema.

## Cached data and deterministic calculations

- Reuse a cached table when it already has the requested columns and scope. For aggregation, ranking, grouping, threshold subsets and comparisons, use `tabulate_cached_result` / `summarize_cached_result`; do not compute from remembered values or sampled rows. Re-query for fresh data or a changed scope/filter, or discover metadata when required fields, asset universe or identity are missing.
- `fetch_cached_result` pages data for display only (`offset`, `limit`); it does not sort or aggregate. Do not page an entire table into the model to calculate it. `summarize_cached_result` computes full-table null counts, numeric min/max/mean, categorical top buckets and capped p50/p95; use `percentileColumns` when needed.
- `tabulate_cached_result` operates on the full table. Use `sorts` (1–3 entries with `fieldName`, `isAscending`), `filters`, `fields`, `offset`, `maxItems` as supported by the selected mode. `group_metric` uses `measures`, optional per-measure `filters`, and optional `derived` / `having` / sorting/projection. For a distribution question (histogram, spread, quartiles, outliers) first run `mode: bin_numeric` (`column` + `binEdges` or `binCount`) or `mode: box_summary` (`column`, optional single `groupBy`); the result table is the chart source, and an EMPTY distribution result must not be charted from an earlier table. Root `where`, `sort`, `limit`, `sortBy`, `direction`, and measure `where` are invalid.
- To retain idle/down assets in utilization or availability calculations, keep the fixed asset universe and filter individual measures rather than filtering all input rows to Running. A filtered sum is zero when a group exists but no row matches that measure. Use `having` for requested group thresholds; sorting a sample does not establish which groups satisfy a threshold.
- `sampleRows` is a preview/page; `totalRows` is the output row count. Neither proves that unseen rows share sampled values. Preserve `sampleOnly`, truncation and coverage limitations.
- Use `analyze_entity_set` for `difference` (left minus right), `intersection`, `union`, or `symmetric_difference`, with explicit `left.cacheId` and `right.cacheId`. Its output has a new `cacheId`. For grouping/filtering/charting, transform that table with `tabulate_cached_result` first, then chart the resulting source; do not assume the set-operation result alone populated `last_invoke`.
- For `LARGE_JSON`, use `inspect_cached_payload` to inspect structure or extract a bounded dotted/index path. For a nested INFOTABLE cell in a cached table, use `extract_nested` with `sourceCacheId` and `cellPath`, then process its new table normally.
- `tabulate_cached_result` / `summarize_cached_result` may use `__PARLER_LAST_QUALIFYING_TABULAR_CACHE__`; it resolves the current turn's qualifying table, then the conversation's remembered table. It does not survive ClearConversation or process restart. Explicit set operands require real IDs. On `LAST_TABULAR_CACHE_UNAVAILABLE` or `CACHE_MISS`, retrieve the required data again or report the gap; do not invent a handle or promise unavailable rows.
- Treat `insightEnvelope` as tool metadata; it is not itself proof of displayed rows or a completed chart.

## Charts and property history

- Numeric `query_property_history` can emit a chart in the same assistant response. Treat emitted charts as delivered; do not offer to create them again, claim they are still being drawn, or refer to them by screen position. Say “the rendered chart shows…” when supported by the result.
- Numeric history text contains compact evidence (`columns`, `sampleRows`, `totalRows`, `sampleOnly` / `rowsOmitted`, `cacheId`), not necessarily every point; do not expect a full `points` array. For `actions`, use the exact `aggregates` object; never infer statistics from samples. Full numeric series can remain in cache and on chart wire. Non-numeric history uses `VALUE_STREAM_HISTORY_INLINE` with bounded samples/cacheId and no automatic chart.
- Send real `startTime` / `endTime` query bounds for a requested interval. `requestedTimeRange: {start,end}` is only a chart-domain fallback when query bounds are omitted; it does not filter retrieved data.
- `build_chart_from_tabular_result` uses a qualifying tabular source: invoke_service INFOTABLE; entity/taxonomy/collection queries or fetch results with rows/cache; or an invoke_service or extended-tool JSON result whose decoded `result` object is a complete small single table. That JSON requires a nonempty root `rows` array of objects, business `status` absent or `success`, no partial-page signal, offset absent/zero, agreeing total/returned counts when present, and rows within the inline limit. Other JSON does not update `last_invoke`. For a distribution (histogram) chart: first run `tabulate_cached_result` mode `bin_numeric` on the numeric column, then build with `kind: histogram` (or `intent: distribution`) and `source: cache_id` set to that result's `cacheId`, with no `xColumn` / `yColumn`; pass `histogramMode: "density"` when the bins have unequal widths and the shape matters. For a spread / quartile / outlier comparison (boxplot): first run mode `box_summary` (optional `groupBy`, at most 24 groups), then build with `kind: boxplot` (or `intent: distribution`) the same way; `yReferenceLines` may add specification limits on the value axis. For a device × period (or any two-key) matrix: first run mode `group_metric` with `groupBy: [rowKey, columnKey]` and one measure, then build with `kind: heatmap`, `seriesColumn` = row key, `xColumn` = column key, `yColumn` = the measure (at most 24 rows × 48 columns; missing combinations stay empty cells, never zero). An EMPTY distribution result must not be charted from an earlier table.
- Supply `source: "last_invoke"` or `"cache_id"`, `xColumn`, and `yColumn` or `series[]`. Use either `kind` (line/bar/scatter) or `intent` (time_trend/rank/compare_groups/correlation/distribution/status_timeline/composition), never both. `orientation: "horizontal"` is only for an explicitly requested horizontal bar chart, not an automatic response to long labels; values and category order are unchanged. `stackMode: "stacked"` / `"percent"` is likewise only for an explicitly requested stacked or 100% bar chart over two or more series (`seriesColumn` or `series[]`); `percent` needs non-negative values, and intents such as composition or compare_groups never stack on their own. When the user explicitly asks for a set of comparable charts (for example one chart per device or per metric), call `declare_chart_group` first with 2–6 named slots, then build each member with `build_chart_from_tabular_result` and its `groupMemberKey`; never declare slots you will not build this turn, and never declare a group for a single chart. Add `sharedCategoryDimension` (for example "utilization state") only when the members break down the same category dimension, so the same category takes the same colour in every member; leave it out when the members measure different or unrelated categories.
- `last_invoke` is the latest qualifying tabular result of the current request (latest-wins; several qualifying results in one turn do not make it ambiguous). It starts empty on each new user request: last turn's numbers in the history does not make them chartable, so run a query first (an explicit cacheId you still hold stays usable). For an earlier table, use its actual returned `cacheId`; a qualifying JSON table can carry one on its outer envelope. Use only a handle a result actually returned and never invent one: evidence ids (e1, e2, …), tool call ids and chartId are never cacheIds. On a cache miss, change source or report the gap; do not retry the same invalid id.
- A turn may emit several charts: Query A → chart A → query B → chart B. `status: success` with `code: CHART_EMITTED` and chartId means delivered — count it as done, do not rebuild it because a later call in the same turn failed, and do not tell the user only one chart per turn is possible. The tool returns a summary; full points travel on chart wire rather than being repeated in tool text.
- For a long cached table, use `seriesColumn` + `yColumn` to chart up to six series with line/scatter/bar; duplicate `(xColumn,seriesColumn)` rows fail. Do not pivot or re-query history solely to assemble a chart when this table already suffices.
- Use `build_history_overlay_chart` for 2–6 live property-history traces on one chart. Each `series[]` resolves its own Thing and window against shared `anchorTime`: explicit bounds, relativeDuration, anchorOffset, or calendarPhrase. Choose `xAxisMode: absolute_time` for the same window, `elapsed_time` for differing windows, and `normalized_time` for shape comparison across unequal durations. The default is absolute for matching windows, otherwise elapsed; normalization must be explicit. `chart_kind` is line (default) or scatter; use `yReferenceLines` for limits. Prefer a suitable existing long cached table over new history retrieval.

## Document knowledge

- Use document tools only when enabled and a document repository is configured. For current asset state, query live tools first. Once a concrete symptom, alarm or component is known, search with `search_document_chunks` using query/signals, then retrieve the top 1–3 sections you will cite using `get_document_chunk`; search snippets alone are not full sections.
- Base manual text and troubleshooting guidance on returned snippet/markdown/sourceLinks only. Cite each source as a Markdown link with its exact `sourceLinks[].href`, preserving any `#page=`. Do not invent text or URLs.
- If search is degraded or has no matches, state that no matching manual section was found and continue from live evidence. When both apply, distinguish observed status, manual guidance, recommendations, and linked sources.
