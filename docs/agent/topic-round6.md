# Topic round 6 — a tool result reaches the model whole, or says plainly that it did not

Topic: `topic-round6`

This document is the proposed design and implementation guide for the sixth round of the agent extension (`parler-agent/`). **Current baseline.** Rounds 1 to 5 are shipped (agent 0.1.251 to 0.1.255; `docs/agent/topic-round1.md` to `topic-round5.md`). This round is about the step between a tool and the model: what the result formatter and `ToolResultEgressGateway` do to a tool result before the model reads it, and one operation that lets a producer see a published document change without waiting for a cache. It is **one design with three independently verifiable slices** (section 5): S1 (R22, R26), S2 (R23, R24, R25), S3 (R27). The six limits it addresses were chosen, after an installation with a custom evidence tool exposed them, by a unanimous vote of four independent reviewers; every other finding stays documentation (section 9). Examples use invented names (`demo-evidence-tool`, `demo-guide`); nothing here depends on a real deployment's data.

**How to read this document.** A fresh implementer reads, in order: the context items below, section 0 (the path a tool result takes, the four places a result is kept, where things are, how tests observe them), section 3 (the decided behaviour), section 6 (the tests and the one fixture recipe) and section 5 (the order). Sections 2 and 4 are the evidence and the hazards behind the decisions. Nothing here asks you to read another review, a conversation or a driver file.

**Design agreement gate:** the Implementor MUST NOT start coding until every User/orchestrator-designated Reviewer agrees with this design in the latest pushed design-agreement round's `### Direction Verdict`, each stating `Fresh-thread readiness: PASS` or `REDIRECT` and an explicit `continue`, `redirect` or `stop`. ## Fresh-thread implementation context

Before changing files, the agent MUST read repo-root `AGENTS.md` and `docs/review-framework.md`.

- **BUSINESS_CONTEXT:** An application team gives the agent evidence tools (extended tools: a service behind an entry of `tools/extended_tools.json`). Whatever such a tool returns is reduced before the model reads it, and the reduction is silent to the answer. In an observed case a tool returned four records of nine fields as JSON (about 5,000 characters) and the model received one string cut at 2,000 characters, so the later records' values never arrived; the answer, and a file it saved, presented the partial table without saying so. The same cut shortens a document page of 2,600 characters that a setting says may be 6,000. A wide table with few rows arrived with **no row at all** and, on the built-in path, no handle to fetch them. The people affected are the model's users (a partial answer that looks complete) and the application teams (a result shape that works in the service and not at the model, with no setting they can change). This round makes a result that fits arrive whole, lets an installation and a tool say how much they need, keeps something useful when a table is too large, tells the model **in the result itself** when anything was reduced, and adds an operation to refresh the document index.
- **CURRENT_IMPLEMENTATION:** `ToolResultEgressGateway.compactForLlmAppend(toolName, toolCallId, raw, log, classification)` is called from `AgentLoop.appendCompactedExecutedToolResultToMessages` (`AgentLoop` l.468, `private static`, called at l.1018 for a cache fault, l.1042 for a running cancel and l.1053 for the normal path: one function, three call sites). It leaves a result alone only when it is at most `LLM_EVIDENCE_CHARS_SOFT_CAP = 8_192` characters **and** contains no `[` (l.117); anything else is parsed and passed through `compactJson`: pass 1 cuts every text node longer than `LARGE_TEXT_EXCERPT_CHARS = 2_000` and samples arrays to `ARRAY_SAMPLE_LIMIT = 20`; pass 2, only if the output is still over 8,192, cuts text at `HARD_TEXT_EXCERPT_CHARS = 512` and arrays to 5; pass 3, only if still over, `compactLastResort` keeps the `PRIORITY_FIELDS` regardless of budget and adds the other fields while the output stays within `LAST_RESORT_TARGET_CHARS = 6_000`; **a field that does not fit is removed from the result, and its omission is recorded only in `_egress.reducedFields`** (`{omitted:true,nodeType}`), not left in place. Markers are added at the top level (`sampleOnly`, `rowsOmitted`, `truncated`, `_egress{reason,rawChars,sampleLimit,reducedFields}`). A service result reaches the gateway through `tools/InvokeServiceExecutor.formatToolResult` (l.622 to 693): an INFOTABLE becomes `{resultKind, rowCount, columns, rows}` (more than 20 rows: `INFOTABLE_LARGE` with `sampleRows` and a cache id); every other type goes through `primitiveOrObjectToJson` (l.900 to 920), which for a JSON value ends in `textNode(String.valueOf(v))`, so a JSON result is **one string field**. Extended tools use `formatDirectServiceResultForLlm` (a cache id on every small table); the built-in `invoke_service` does not. A document page is read by `tools/DocumentKnowledgeRuntime.executeGetDocumentChunk`, which truncates `markdown` at `documentKnowledgeChunkMaxChars` (default 6,000, allowed up to 500,000) before the result is serialized. The document index lives in the static `tools/DocumentKnowledgeIndexCache`, refreshed only when its entry expires (`documentKnowledgeIndexTtlSeconds`). A tool that a person approved (HITL) does **not** pass through this call: it executes in `AgentThing`'s approve continuation, and its result is appended whole by `HitlSyntheticToolResultAppender.appendDurable` (section 0 traces it). Sections 0 and 2 give the verified facts and their locations.
- **TERMS_AND_CONTRACTS:** A *reduction* is anything that makes the model see less than the tool returned; its signs are, at the **root** of the result envelope: `truncated`, `sampleOnly`, `rowsOmitted` set true, `resultKind` `INFOTABLE_LARGE` or `RESULT_OVERFLOW`, `readLimitReached` true, a `warnings[]` entry with code `CHUNK_MARKDOWN_TRUNCATED`; `_egress.reducedFields` says what the gateway removed. `_egress` alone is **not** a reduction: it can carry only a data classification; and a field named `truncated` nested inside a tool's own business object is **not** the transport contract. *Gateway reduction* means the gateway changed the result; *producer reduction* means the tool or formatter already returned a partial result (a table sample, a truncated page). The *effective soft cap* is the serialized size (UTF-16 code units, escaping, markers, note and classification included) above which the gateway reduces; the *effective text cap* is the size above which one text node is cut once it reduces. A *table-shaped result* is a root object with `columns` and `rows` (or `sampleRows`). A *cache id* is a handle to a stored full result; it is **not** a sign that rows were left out (extended tools give one to every small table). Contract files are `CONTRACTS/*.md`; a change to a tool-result shape needs an entry in `CONTRACT_VERSION.md` in the same commit. `docs/agent/configuration-repository.md` owns `extended_tools.json`, `AgentSettings` and `features`; `docs/agent/document-chunk-tools.md` owns the document tools and the index. Section 10 is the glossary.
- **DEPENDENCIES_AND_HANDOFFS:** Rounds 1 to 5 on the integration branch. Consumers of the new behaviour: application authors (they may declare a per-tool text cap, R24) and external generators and test drivers that read `features` and the snapshot from `GetAgentRuntimeSnapshot`. No other topic depends on this one. A separate reference document, "Limits and budgets of the agent", describes the limits this round does not change (section 9); it is not part of this work. No prior conversation, review packet or driver file supplies implementation knowledge.
- **SCOPE_AND_BOUNDARIES:** Implement R22 to R27, the features of section 3, and P35 to P42, in the three slices of section 5, each ending with the full local command green. Do not change: the 7,000-unit topic body and the 8,192 topic carrier (`TopicMethodText`), the 65,536-character large-JSON classification cap, the sample limit of 20 and its exemptions, the replay compactor (`LlmToolResultReplayCompactor`), `fetch_cached_result` and `tabulate_cached_result` paging, the stream persistence caps, the topic lane and its scoring, approval and policy behaviour, the error-envelope rule, search limits. Section 1 lists what is out of scope.

(D3) In `node` mode a custom tool's JSON result obeys the same gateway rules as any built-in object result, including sampling of arrays longer than 20; authors who return a list should return a table. (D4) The gateway's entry is the **serialized size after array sampling**; a result at or under the effective soft cap is never cut in text (R23). (D5) The installation chooses the soft cap; a tool may declare only its **text** cap, inside it; the soft cap is **never raised for a page or a tool**; one `ResultBudget` is resolved **once per tool call, when the call starts executing** (ordinary or approved), stored by tool call id, and used by the formatter's cache decision and by the gateway, even if a setting changes meanwhile; its values and sources appear in the snapshot (R24). (D6) The soft cap's range is 8,192 to 65,536 with default 8,192, because a topic carrier of up to 8,192 characters must never be reduced; 65,536 is a chosen installation ceiling, not a recommendation. (D8) A cache that cannot be prepared is reported (`recovery:"unavailable"`, no `cacheId`), and the model is told to ask the tool for less, not to read a cache that does not exist. (D9) The completeness note is in the result, fires on any reduction at the envelope root (gateway **or** producer), is reserved in the budget, and replaces the raw result even when the annotated result is longer than the raw one (R26). (D10) The stream-persistence order of rows is documentation only; no test of this round may depend on the order in which the stream writes rows. (D11) The refresh service invalidates one key lazily and a rebuild that began before the invalidation must not repopulate it (R27). (D12) The default soft cap and text cap stay 8,192 and 2,000. (D13) **No margin above the soft cap.** Every first append is at most the effective soft cap after escaping, classification and the note, **including the overflow response**, which is itself built within the cap (R23); the only stated exceptions are the error envelope (unchanged) and an overflow envelope whose **minimal** form (the fixed fields, the note and the retained author-supplied classification stamp, with no names and no hint) itself exceeds the cap (R23). (D14) **The approved path is part of the work, not a recorded gap:** S1 adds the note to an approved result that shows a reduction and changes nothing else (no new size cut); S2 sends the approved result through the gateway once, with the budget captured at its execution, before `appendDurable`; the docs state the one deliberate change (an approved result over the soft cap is now reduced where it used to arrive whole) (R26d). (D15) Not this round: flipping the default of `toolResultJsonMode`, and a per-tool opt-out of array sampling.

## 0 Primer for a fresh implementer

**What runs.** The agent is a ThingWorx extension (`parler-agent/`). A turn is a loop in `AgentLoop`: it sends the conversation to a model provider, the model answers with text or tool calls, the loop executes the tools, **appends each tool result as a message**, and sends again, until the model answers in text. Tools are built-ins (`invoke_service`, the document tools, the cached-table tools) and extended tools declared by the application in `extended_tools.json`.

**The path of a tool result** (this round lives on it):

```text
service (ThingWorx)                                 ValueCollection with the service's result type
  -> built-in invoke_service:  InvokeServiceExecutor.doInvokeService  l.382   formatToolResult(..., false)
                                                    l.383 maybeRejectOversizedInvokeServiceResult (65,536; exempts INFOTABLE*)
  -> extended tool:            AgentThing.executeExtendedTool l.4466 -> executeExtendedToolOnThing l.4517
                                                    l.4562 formatDirectServiceResultForLlm -> formatToolResult(..., true)
  -> back in AgentLoop         l.1053 appendCompactedExecutedToolResultToMessages (l.468)
                                                    l.479 ToolResultEgressGateway.compactForLlmAppend   <- reduces
  -> the compact string is the tool MESSAGE appended toward the model (the "first model append")
```

**The approved path** (a HITL-gated tool a person approved; traced at 0.1.255, paths in `AgentThing` and `AgentLoop`): the approve continuation executes the tool itself (l.2150 an extended tool through `executeExtendedTool`, l.2169 `invoke_service` through `InvokeServiceExecutor.executeInvokeService`, `set_property_value` through `SetPropertyValueExecutor`; a registry miss, a failure or an unsupported gate yields its own result string). `TabularChartRoundHooks.augmentJsonSourceHandle` adds the chart handle to that string (l.~2199). `HitlSyntheticToolResultAppender.appendDurable` (l.~2202, class l.36 to 54) then adds the string **unchanged** to the in-memory `messages` and to the stream row. The same raw string seeds `HitlEvidenceSeed` and is `completedGatedResult`, which `AgentLoop.runInner` (l.~523) replays into the chart and task state; `runParlerPostToolAgentLoop` (l.1785) and `AgentLoop.runAfterApproval` (l.375) then continue the turn. **Nothing on this path calls `compactForLlmAppend`**, so an approved result of any size reaches the next model request whole, and a producer's own sample or cut page gets no note. Cancel, reject, expiry and the interrupted siblings append synthetic rows and are not tool results. Existing tests of this path: `HitlSyntheticToolResultAppenderTest`, `AgentLoopHitlContinuationChartSourceTest`, `ParlerHitlContinuationContextTest`, and `AgentLoopTestFixtures.runAfterApproval`.

## 1 What this change is for

A tool result is the model's evidence. Today four things make it unreliable in a way that neither the application author nor the model's user can see or change: a small result is cut (a JSON result is one string cut at 2,000; any `[` sends a short result into compaction), the cut is silent to the answer (the markers exist; nothing makes the answer report them, and a producer's own partial result gets no note at all), a table that is too large shows no row and, on the built-in path, no handle, and the budgets are constants nobody can set. A fifth, smaller thing slows every producer: a published document is found only after a cache lifetime, and nothing refreshes it.

### In scope (round 6)

- **R22** A JSON result can be delivered as a JSON value (installation opt-in).
- **R23** The gateway decides from the serialized size after array sampling; a result at or under the soft cap is never cut in text; an overflow that cannot be reduced gets a response that is itself within the budget (no margin).
- **R24** The soft cap and text cap are settings, a tool may declare its text cap, one resolved budget is used by the formatter and the gateway, and its values are visible.
- **R25** A table that is too large keeps whole rows, filled to the budget, and a usable handle (or says it has none), on both paths and for the formatter's own sample.
- **R26** A reduced result says so in the result itself; a contract defines the markers and the lanes; a standing sentence repeats it; the approved-continuation path, which skips the gateway today, gets the same note (S1) and the same budget (S2).
- **R27** An operation refreshes this agent's document index and reports what it did; the snapshot shows the index state and the numeric document-index settings.
- **F** The `features` names, one slice at a time.

### Out of scope (do not do these)

- Raising the 7,000-unit topic body or the 8,192 topic carrier, the 65,536 large-JSON cap, the sample limit of 20, `fetch_cached_result` or `tabulate_cached_result` paging, the stream persistence caps, or changing the replay compactor.
- Changing the error-envelope rule: an error envelope keeps today's entry (over 8,192 or a `[`) and its single pass (arrays 5, text 512).
- Changing the topic lane, its scoring or the way signals and tags match.
- A new model-facing tool, or any change to approval, policy or HITL **behaviour**: the approval protocol, outcomes and side effects are untouched; only the string presented to the model after an approval changes (R26d).
- Making the model comply: a sentence in a prompt, and a note in a result, are guidance. This round promises nothing more.
- Clearing the document index on `DisableThing`, `EnableThing` or `RestartThing`, or switching document caching off; reordering what the stream writes (D10).
- Editing published changelog entries or anything under `docs/archived/`.

## 2 Verified facts this design relies on

Read at `nearterm` (agent 0.1.255); paths under `parler-agent/src/main/java/com/thingworx/things/agent/` unless noted.

1. **Entry.** `ToolResultEgressGateway.compactForLlmAppend` (l.109 to 140) returns the result unchanged only if `raw.length() <= 8192 && raw.indexOf('[') < 0` (l.117). An error envelope (`status` "error" or a root `error` key, `isErrorEnvelope` l.496) that enters compaction takes one pass (arrays 5, text 512, `compactErrorEnvelope` l.218). Text that does not parse is compacted only above 8,192, as a `LARGE_TEXT_COMPACT` excerpt of 2,000 characters with `truncated:true` and `rawChars` and no `_egress` object (l.231). The only main-code caller is `AgentLoop` l.479.
2. **Passes** (`compactJson`, l.183 to 216): pass 1 text 2,000 and arrays 20; pass 2, only if still over 8,192, text 512 and arrays 5; pass 3, only if still over, `compactLastResort` (l.350 to 419). The compacted form is kept only if strictly shorter than the raw result (l.212): an annotated result that is longer than its input is discarded and the raw result returned.
3. **A cut text field is enough** to set `sampleOnly`, `rowsOmitted` and `truncated` (`truncatedTextFields`), even for non-tabular JSON. `applyTopLevelMarkers` (l.460 to 474) sets them; `truncated` is `put` and overwrites a root `truncated`; `_egress` carries `reason`, `rawChars`, `sampleLimit` and `reducedFields`, the latter collapsed to a summary above 2,000 characters.
4. **Pass 3 removes.** For an object root (l.350 to 419): `keepsThroughLastResort(name, value)` is `PRIORITY_FIELDS.contains(name) || isReadLimitEvidence(name, value)`, decided on the original value; a kept field is written regardless of budget; any other field is written only while the output stays within 6,000 characters (`putWithinLastResortBudget` l.438), otherwise it is **absent from the result** and `{omitted:true,nodeType}` (plus `originalCount`, `returnedCount:0` for an array) is recorded in the `reducedFields` markers. A non-kept array whose name may be sampled becomes a sample of 5; a non-kept object of 1,500 characters or less is compacted. `PRIORITY_FIELDS` (l.34 to 40) include `status`, `code`, `resultKind`, `cacheId`, `totalRows`, `returnedRows`, `sampleOnly`, `rowsOmitted`, `columns`, `warnings`, `hint`, `message`, `completeness`, `reason`; **not** `rowCount`, `rows`, `sampleRows`. So a table whose `columns` are many arrives with `columns` and **no row**.
5. **Table-shaped results have no structural detection.** `shouldSampleArrayField` (l.289) and `isSchemaOrMetadataArrayField` (l.341) work by name: `columns`, `dataShape`, `fieldDefinitions` are never sampled; `rows` and `sampleRows` are. Read-limit evidence (`readLimitReached`, `readLimitNote`, `readLimitReachedSeries`, `source/ReadLimitFact`) is kept through every pass by name and value shape.
6. **Call sites.** Built-in path: `doInvokeService` l.382 `formatToolResult(..., false)`, l.383 `maybeRejectOversizedInvokeServiceResult` (65,536; exempt when `resultKind` starts with `INFOTABLE` or a `cacheId` exists), return l.386. Extended path: `AgentThing.executeExtendedTool` (l.4466, holds the `ExtendedToolDefinition`) -> `executeExtendedToolOnThing` (l.4517, receives only the service name) -> `formatDirectServiceResultForLlm` (`InvokeServiceExecutor` l.700) -> `formatToolResult(..., true)`; no 65,536 check on this path. Both then reach `AgentLoop` l.1053. `AgentLoop` l.475 to 479 obtains the data classification through `AgentToolContext.getAgentThing()` and `AgentThing.capabilityDataClassificationForTool` (~l.4492), and skips it when the agent is null. **A HITL-approved tool executes at `AgentThing` l.2150 (extended) and l.2169 (`invoke_service`) outside this call and is appended by `HitlSyntheticToolResultAppender.appendDurable` without the gateway** (section 0, R26d, hazard 10).
7. **JSON result.** `formatToolResult` builds `{status, resultKind, result: primitiveOrObjectToJson(raw)}` for every non-table type (l.675 to 692); `primitiveOrObjectToJson` (l.900 to 920) handles String, numbers, Boolean, DateTime; everything else becomes `textNode(String.valueOf(v))` (l.919). The SDK's `JSONPrimitive` holds an `org.json.JSONObject` (javap on `twx-lib/9-7`); the repository's SDK jar is a stub, so the unwrap of `ValueCollection.getValue` is **inferred, not run**: the implementer confirms it against the real library, and the User's live check (section 8, step 1) confirms it on a server. `tools/TabularChartRoundHooks.decodeBusinessObject` (l.558) accepts object nodes and textual objects. No test covers JSON result formatting.
8. **Table path.** More than `LARGE_TABLE_ROW_THRESHOLD` (20) rows: `cacheLargeTable` (l.1136 to 1168) returns `{status, resultKind:"INFOTABLE_LARGE", totalRows, columns, sampleRows (first 20 rows), cacheId, hint, entityName, serviceName}`. If sanitising the copy fails, `cacheId` stays null, the samples come from the unsanitised table and the hint reads "Large result; paging via fetch_cached_result is unavailable (cache copy could not be prepared)."; `TabularArtifactHub.store` itself throws (built-in: `errorJson`; direct: `SERIALIZATION_FAILED` or a rethrown repository fault). Otherwise `fullTableJsonNode` (l.922) gives `{status, resultKind:"INFOTABLE", rowCount, columns, rows}` and, when the boolean is true, a `cacheId`. A cache id on a small table is **not** a reduction sign.
9. **Document page.** `executeGetDocumentChunk` -> `buildGetSuccess` (l.~735 to 766) returns `{status, degraded, docId, chunkId, heading, sectionPath, contentType, pageStart, pageEnd, markdown, sourceLinks, warnings}`. If `markdown.length() > chunkMaxChars` it is cut to `substring(0, max-1) + "…"` **before serialization** and `warnings` gets `{code:"CHUNK_MARKDOWN_TRUNCATED", message:"Chunk markdown was truncated to the configured maximum."}` (the code string exists only inline; there is no `truncated` boolean on this result). The result is serialized with Jackson defaults: each newline, quote and backslash costs two characters, control characters six, non-ASCII none. No test covers the truncation.

## 3 Required behaviour

### R22 A JSON result can be a JSON value (S1, opt-in)

A new `AgentSettings` field `toolResultJsonMode` (STRING, `string` or `node`, default `string`, read live; any other value resets to `string` with `CONFIG_VALUE_CLAMPED`). In `node` mode `formatToolResult` converts a result whose base type is JSON to a Jackson node and puts it in `result`: `{status, resultKind:"JSON", result:{...}}`; a value that cannot be read as JSON falls back to the string, with no error. A STRING result stays a literal string in both modes. In `string` mode nothing changes. Both invocation paths pass through the same function, so both honour the mode. The feature `tool-result-json-node/1` announces that the build **supports** the mode; the snapshot (`tools.resultJsonMode`) shows which mode is active. **Why opt-in:** the shape every JSON tool returns changes, and an author may depend on the string. **Consequence to state in the docs (D3):** in `node` mode a custom tool's arrays longer than 20 are sampled, with markers and the note, like any built-in object result; a tool that returns a list should return a table.

### R23 The gateway decides from the serialized size after sampling, and never exceeds the budget (S2)

Replace the entry rule for JSON results. The error-envelope rule keeps its shape and is the stated exception to the ceiling below; plain text uses the effective soft cap in place of the constant. The procedure: (1) parse once; (2) sample eligible arrays to 20, with today's exemptions (schema arrays, the read-limit series, the alert-summary fields), recording markers; (3) build the candidate envelope **with** its markers, the completeness note (when R26b applies) and the classification stamp, and measure it in UTF-16 code units; (4) if that size is at most the effective soft cap, return it, with text uncut; if nothing was sampled or annotated, return the raw string byte for byte; (5) otherwise reduce: a **table-shaped root** by the whole-row fill of R25b; any other root by pass 1 (text cut at the effective text cap, arrays 20), then pass 2 (text 512, arrays 5) while still over, then pass 3 while still over; (6) **no margin:** if after step 5 the serialized size still exceeds the effective soft cap (pass 3 keeps priority fields regardless of budget; a table's `columns` and the note are protected), replace the result with the **budgeted overflow response**.

**The overflow response** is built the way a table is filled: first the fixed part `{status:"success", resultKind:"RESULT_OVERFLOW", rawChars, cacheId (if any) or recovery:"unavailable", completenessNote, hint}` plus the classification stamp; then the names that fit, `columnNames` for a table-shaped root and `fieldNames` (the root's field names) otherwise, added **one at a time, in source order, while the serialized envelope, escaping included, stays within the effective soft cap**; when some are left out it states `columnNamesOmitted` or `fieldNamesOmitted` (a count). No count limit applies to the names: only the cap does. Each variant of the note is at most 1,200 characters and the hint at most 400, so the fixed fields **without the classification stamp** are under 2,000 characters. `RESULT_OVERFLOW` is a reduction sign (R26a). **The ceiling:** the serialized first append is at most the effective soft cap for every result except (i) an error envelope, whose entry and single pass are unchanged, and (ii) a result whose **minimal overflow envelope** (the fixed fields, the note and the retained author-supplied `dataClassification` stamp, with no names and no hint) exceeds the cap: the parser does not bound the stamp, and a stamp that fits by itself can still push the fixed fields over the cap. That minimal envelope is returned and `_egress.reducedFields.overBudget:true` says so. The classification is preserved, not bounded; bounding it is not part of this round. P37 asserts the ceiling at sizes around the cap and for escaping-heavy names.

**An annotated result always replaces the raw one when any reduction occurred, even if it is longer than the raw one** (today it is discarded in that case, fact 2). A `[` inside a text field no longer matters. **Consequence to accept:** results between 2,000 and the soft cap arrive whole, so a turn's context grows by up to about 8,192 characters per such result; the replay compactor and `llmContextMaxChars` still bound the conversation, and the first append is bounded by the soft cap.

### R24 Budgets are settings, may be declared per tool, and are resolved once per call (S2)

- Two `AgentSettings` fields, read live, in a new `ToolResultSettings` modelled on `DocumentKnowledgeSettings`: `toolResultSoftCapChars` (default 8,192; 8,192 to 65,536) and `toolResultTextCapChars` (default 2,000; 500 to 50,000). The text cap is clamped to at most the soft cap minus 1,024. Below a minimum resets to the default, above a maximum clamps, both with `CONFIG_VALUE_CLAMPED`. The pass-2 and pass-3 constants (512, 6,000, sample 5) do not become settings.
- An optional `resultTextCapChars` on an `extended_tools.json` entry, parsed in `ExtendedToolsManifest.load` beside `executorOnly` (it is **not** a capability field: a legacy entry with only `name`, `whenToUse`, `target` and this field stays valid and `risk` does not become required). A non-integer or non-positive value **skips that entry** (the existing `skipEntry` rule); an integer outside the legal range is clamped with `CONFIG_VALUE_CLAMPED`. It overrides the **text cap** for that tool's result only; it never raises the soft cap.
- **Precedence, one order:** (1) the installation's soft cap is the ceiling of every result; (2) the text cap is the tool's declared value if valid, else the installation's, clamped as above; (3) a document page has **no exception**: a page is delivered whole when its serialized envelope (escaping included) fits the effective soft cap, otherwise it is reduced like any result and the note says so. An installation that wants pages near its page setting raises `toolResultSoftCapChars`. The snapshot warning `CONFIG_PAGE_EXCEEDS_RESULT_CAP` appears when `documentKnowledgeChunkMaxChars` plus 1,500 exceeds the soft cap; **it is an estimate that ignores escaping** (a page of 5,500 quote and backslash characters can serialize to about 11,000 in a small envelope), so its absence promises nothing: the result itself carries the note whenever it was reduced. The page setting (the producer's own truncation, `CHUNK_MARKDOWN_TRUNCATED`) is unchanged.
- **One budget per call, resolved when the call starts executing.** A `ResultBudget {softCapChars, textCapChars, source}` is produced by a `ResultBudgetResolver` (`resolve(toolName)`); production supplies it from `AgentThing` (settings, and the extended-tool registry for `resultTextCapChars`); tests supply a lambda. It is resolved **exactly once per tool call**, in the one place that starts the execution: `AgentLoop` before it dispatches a call (it gains a constructor overload taking the resolver; existing constructors use a default resolver), and the approve continuation in `AgentThing` before it executes an approved tool. It is stored in `AgentToolContext` by tool call id and read by both consumers: the formatter (`InvokeServiceExecutor.formatToolResult` and `formatDirectServiceResultForLlm` gain a budget parameter; the built-in and extended execution paths read it from the context by the call id they already hold) and the gateway (`compactForLlmAppend` gains a budget parameter). It is removed after the first append or the approved append (in a `finally`) and by `AgentToolContext.clear()`. **A setting that changes after the call started does not affect that call.** A consumer that finds none (a tool without a formatter, such as the document tools; a direct gateway call; the playbook path) asks the resolver once for that tool, and with no resolver uses the defaults. The R25a formatter decision and the gateway therefore always judge the same object.
- The snapshot `tools` block gains `resultJsonMode` and `resultBudget {softCapChars, textCapChars, perTool:[{name, textCapChars, source}], warnings}`, where `source` is `default`, `setting` or `tool`. The feature is `tool-result-budget/1`.

### R25 A table that is too large keeps whole rows and a usable handle (S2)

- **(a) Cache before reduction, with room for the envelope.** After the formatter builds a table result, if its serialized size **plus a reserve of 1,536 characters** (the note, the markers and the classification stamp that the gateway adds) exceeds the effective soft cap, a cache is prepared and `cacheId` added **on both paths** (the extended path already gives one to every small table; the built-in path does not). The decision uses the call's `ResultBudget`. The 20-row sample of `INFOTABLE_LARGE` is produced as today. A table that fits with the reserve is not cached and arrives whole.
- **(b) Whole rows, filled greedily.** For a table-shaped root, `rows` and `sampleRows` are reduced only by dropping **whole rows**, never a cell (the text cap does not apply to cells of a table-shaped root; a cell above the cap simply means that row does not fit). The procedure: write the protected fields first (`status`, `resultKind`, `columns`, `cacheId` or `recovery`, the totals, `completenessNote`, the classification stamp); then add rows **in source order, one at a time, while the serialized envelope stays within the effective soft cap**; stop at the first row that does not fit. The result may keep no row. It states `returnedRows` and the total (`totalRows` for `INFOTABLE_LARGE`, `rowCount` otherwise), and `rowsOmitted:true` when any row was left out. Other text fields of the root are cut at the text cap as usual. If the protected fields alone exceed the cap, R23 step 6 applies (the overflow response, built the same way over `columnNames`). There is no head-allowance constant, no partial row and no `rowsPartial`. The producer note says "a sample of N of M rows" and N depends on the fill: measure the fill with M in place of N (at least as many digits), then write the final note.
- **(c) Honest recovery.** If a cache id exists, the note says to ask the tool for less or to read the cached result: for a wide table, `tabulate_cached_result` with `mode:"filter_sort_topn"`, a `sorts` entry and `fields` (every column you name, for up to `maxItems` rows, default 50 and at most 500, paged with `offset`; `filter_rows` would also need `filters`, `group_metric` aggregates; the note's recovery clause says the same and does not promise all rows), **listed before** `fetch_cached_result`, whose pages of more than 4,096 characters of row text are themselves reduced to a sample (fact 14). **Whenever the gateway drops rows and the result has no `cacheId`, it carries `recovery:"unavailable"`** (cache preparation failed, fact 8; or the formatter judged that the table fit and a later addition made it not), and the note says only to ask the tool for less (fewer fields, a narrower request). Never tell the model to read a cache that does not exist. The feature is `tool-result-table-recovery/1`.

### R26 A reduced result says so (S1; its approved-path part, R26d, completes in S2)

- **(a) A contract.** `CONTRACTS/TOOL_RESULT_COMPLETENESS.md`, with an entry in `CONTRACT_VERSION.md`: the signs of a reduction **at the envelope root** (`truncated`, `sampleOnly`, `rowsOmitted` true; `resultKind` `INFOTABLE_LARGE` or `RESULT_OVERFLOW`; `readLimitReached` true; a `warnings[]` entry with code `CHUNK_MARKDOWN_TRUNCATED`; `_egress.reducedFields`, `_egress.rawChars`); that **`_egress` alone is not a reduction** and a business field nested below the root is not the contract; the three states an answer must keep apart (evidence the model did not see, a value the source does not have, a value recovered by a later read); the four places a result lives and which one each statement is about (section 0); and the note's text.
- **(b) The note, in the result.** Whenever the envelope root shows a reduction, from the gateway **or** from the producer (the formatter's table sample, a truncated page, read-limit evidence, an overflow response), the gateway adds the text field `completenessNote` (a priority field, kept through every pass, counted in the size of R23 and reserved in the budget; each variant is at most 1,200 characters). Four variants: gateway cut ("This result was reduced before you saw it (see truncated, rowsOmitted, _egress.reducedFields). Say in your answer which values or rows did not arrive, and say the same in any file you save. Do not present it as complete. …"), producer sample or table ("This result is a sample of N of M rows. …"), page ("This page was cut at the configured maximum. …"), overflow ("This result was too large to show; only its shape is given. …"), each ending with the recovery clause of R25c (ask the tool for less, with the cache or projection route only when a handle exists, or a smaller page for a page). It is in the result, so it applies when an external system prompt replaces the routing guide. A producer reduction that the gateway does not otherwise change still receives the note (the entry of R23 annotates without reducing).
- **(c) A standing sentence.** The same instruction, shortened, is added to the routing guide and to `FINAL_ANSWER_EVIDENCE_RULE`. **What this does not do:** a model can still ignore it; (b) is the guidance that arrives with the evidence it is about. The feature is `tool-result-completeness/1`.
- **(d) The approved path (S1 and S2).** Section 0 traces it: an approved tool's result is appended whole by `HitlSyntheticToolResultAppender.appendDurable`, with no gateway call, and the same raw string feeds the chart handle, `HitlEvidenceSeed` and the resumed loop's hooks. **Required landing:** a new package-private class `ApprovedToolResultAppender` with one static method that takes the messages, the call id, the executed tool name, the raw result (**the output of `augmentJsonSourceHandle`**, so the presented row, the history and the next model request carry the same chart `cacheId`, which every reduction protects), the classification, the call's `ResultBudget`, and the stream keys, **finalizes the string once** and calls `appendDurable` with it; the approve continuation calls it in place of `appendDurable`. It does not re-execute the tool and does not compact twice. *S1:* it adds `completenessNote` when the envelope root of the raw result shows a reduction (a producer's sample or cut page) and otherwise returns the raw string **byte for byte**: no new size cut. *S2:* it sends the raw result through `compactForLlmAppend` with the budget captured at the approved execution (R24), so an approved result gets the same reductions, the same overflow response and the same note as an ordinary one; when it reduced, it stores the full body with `AgentToolContext.setToolEgressFullJsonForToolCall` exactly as the ordinary path does. **What stays raw:** the string given to `augmentJsonSourceHandle` (which runs first, as today), to `HitlEvidenceSeed`, to `completedGatedResult` and to the chart and task-state hooks; only the string given to `appendDurable` is the presented one, so approval outcomes, the `executed` flag, the audit log and every side effect are independent of presentation. Cancel, reject, expiry, unsupported-gate and interrupted-sibling rows are synthetic and unchanged. **The deliberate change to document (S2):** an approved result over the soft cap is now reduced where it used to arrive whole; one that fits arrives whole as before.

### R27 The document index can be refreshed, and the refresh can be seen (S3)

A service `RefreshDocumentKnowledgeIndex` on `AgentThing`, beside `RefreshTaxonomyCache` and mirroring it (no parameters, result a JSON STRING, platform per-service permissions, no new permission code). It resolves this agent's key (`name|repository|rootPath`) and calls a new `DocumentKnowledgeIndexCache.invalidate(key)`. Result `{invalidated, evictedIndexLoadedAt, ttlSeconds}`: `invalidated` is true exactly when an entry was removed; `evictedIndexLoadedAt` is that entry's load time, or null when there was none. It does not rebuild: the next document search does, lazily. **A rebuild that began before the invalidation must not repopulate the cache:** keep a per-key generation counter; `invalidate` increments it **and removes the entry in one critical section**; `getOrLoad` captures the generation before `rebuildIndex` and publishes through `publishIfCurrent(key, generation, entry)`, which, in **the same critical section** (a per-key lock or `ConcurrentHashMap.compute`), compares the generation and puts only if it is unchanged; otherwise the rebuilt index serves that one call and is not stored. A compare followed by a separate `put` would let an invalidation fall between them and is not acceptable. Another key (another agent, repository or root) is untouched. After an invalidation a failed rebuild has no stale index to serve and fails as a first load does. `GetAgentRuntimeSnapshot` gains a root block `documentKnowledge` with the numeric document-index settings and `index {loadedAt, expiresAt}` or `null`, read through a new `DocumentKnowledgeIndexCache.peek(settings, agent)` that never triggers a load. The lifetime stays a setting; `DisableThing`, `EnableThing`, `RestartThing` and `RefreshPromptContextCache` still leave the cache alone, and the documentation says so. The feature is `document-index-refresh/1`.

| `page-0002` (escaping; serialized 9,000 to 12,000), soft cap 8,192 | cut at 2,000 | the same cut, plus the note | **reduced, with the note** (its serialized envelope is above the cap); **whole** at a soft cap of 16,384 |
| An **approved** result over the soft cap | whole, no note | whole, no note unless a root sign is present | reduced as an ordinary result under the captured budget (the documented change) |
| An **approved** producer sample (`INFOTABLE_LARGE`) | whole, no note | whole, plus the note | as an ordinary result |

## 9 Decisions, and what is deferred

- **Decided (section CARRIED_DECISIONS D1 to D15).** Reasons: three slices so each can be accepted alone and the markers' contract exists before budgets depend on it (D1); an opt-in for R22 because the shape every JSON tool returns changes, while R23 to R25 change behaviour only for results that were being cut (D2, D3, D4); the installation owns the ceiling and a tool only its text cap, so no page or tool silently enlarges what an installation allowed (D5, D6); whole rows only, because a cut cell looks like a value and a partial row is a second kind of missing cell (D7, D8); the note travels with the result because a standing sentence is skipped in external-prompt mode, and it fires on producer reductions too because the model cannot tell who reduced it (D9); the stream's write order is documentation (D10); a refresh must not be undone by a rebuild already in flight (D11); no margin above the cap and a response that is itself budgeted, so one promise holds everywhere (D13); the approved path is a result-delivery path in the stated scope and gets the note first and the budget second, so S1 does not cut what arrives whole today (D14).
- **Deferred, documentation only (the reference document):** the sample limit of 20 and its exemptions, the last-resort pass, error-envelope compaction, the 7,000/8,192 topic bounds, the topic lane's rules, approval frames and their life, title versus conversation id, the rehydration defaults, the order in which the message stream is written, `fetch_cached_result` and `tabulate_cached_result` paging.
- **Closed by the first design-agreement round (all four reviewers):** the `RESULT_OVERFLOW` margin (none: D13) and the head allowance (a greedy whole-row fill replaces it: D7); the approved-continuation path (a landing, D14, P42); the per-slice expectations (section 5A). **Not this round (D15):** whether the default of `toolResultJsonMode` flips later, and a per-tool opt-out of array sampling; each needs its own evidence.

## 10 Glossary

- **reduction** — anything that makes the model see less than the tool returned; read at the envelope root (section 3, R26a).
- **gateway reduction / producer reduction** — the gateway changed the result / the tool or formatter already returned a partial one.
- **effective soft cap / text cap** — the serialized size (UTF-16 units, escaping, markers, note, classification) above which the gateway reduces / above which a text node is cut once it reduces.
- **table-shaped result** — a root object with `columns` and `rows` or `sampleRows`.
- **whole-row fill** — the rows of a table kept, in source order, while the serialized envelope stays within the effective soft cap; possibly none.
- **overflow response** — `RESULT_OVERFLOW`: the fixed fields, the note and the names that fit, itself within the cap.
- **captured budget** — the `ResultBudget` resolved once when a call starts executing and used by both the formatter and the gateway for that call.
- **approved path** — the continuation after a person approves a gated tool; it appends the result through `ApprovedToolResultAppender` (R26d).
- **cache id** — a handle to a stored full result; not a sign that anything was left out.
- **first model append** — the tool message the loop appends toward the model; the persist row starts identical; the UI lane may hold the full body.
- **slice** — one of S1, S2, S3: an independently verifiable part of this one design.
