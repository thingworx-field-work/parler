# Chart intent

Parler charts are built from validated data and explicit visual intent, never from free-form prose. This
document describes chart identity (`chartId`), intent-driven kind selection in
`build_chart_from_tabular_result`, and the neutral chart wording given to the model.

Wire shapes belong in [`CONTRACTS/CHART_CONTRACT.md`](../../CONTRACTS/CHART_CONTRACT.md); rendering belongs in
`parler-ui`. Pie charts, grouped bars through `seriesColumn`, share operations and chart rescue are in
[`prompt-to-chart.md`](./prompt-to-chart.md) §7–8; several charts per turn in
[`multi-chart-and-thrashing-safeguards.md`](./multi-chart-and-thrashing-safeguards.md) §4.

## Chart paths

Parler has three chart paths:

- `query_property_history` returns numeric history; `ParlerChartWireSupport` derives and emits a chart frame.
- `build_chart_from_tabular_result` builds a chart from a qualifying tabular result or a `cacheId` through
  `BuildChartFromTabularResultExecutor` and `ParlerTabularChartBuilder`.
- **`build_history_overlay_chart`** overlays **2–6** history series on one chart — same-window cross-Thing
  (`absolute_time`) or shifted windows (`elapsed_time`). Design:
  [`history-overlay-chart.md`](./history-overlay-chart.md); wire rules: `CONTRACTS/CHART_CONTRACT.md` §3.0e.

`ChartBlock.kind` is one of:

- `line`
- `bar` (optionally `orientation: "horizontal"`, and `stackMode: "stacked" | "percent"` for two or more series)
- `scatter`
- `pie` (explicit `kind` only; no intent selects it — see `prompt-to-chart.md` §8)
- `histogram` (over a `bin_numeric` result table)
- `boxplot` (over a `box_summary` result table)
- `heatmap` (over a two-key long table such as a `group_metric` result; explicit `kind` only)

Inside an assistant row the UI renders chart and table blocks before the final Markdown. The model is
therefore told not to refer to charts by screen position (see "Neutral wording").

## Neutral wording

The routing guide treats an emitted chart as already visible in the same assistant row. The model does not
offer to create it again, does not claim it is still being drawn, and does not refer to it by screen position
(below, above, following). It uses neutral wording such as "the rendered chart shows…".

## `chartId`

`ChartBlock` has an optional `chartId` so a final answer and exported output can refer to charts by a local id.

- Generated by the agent, never by the model.
- Simple local ids: `c1`, `c2`, `c3`. Not globally unique.
- Scope: one user request. The counter lives in `TabularChartRoundState` (`nextChartId()`, reached through
  `AgentToolContext.nextParlerChartId()`); it is reset at the start of each user request and carried across an
  approval pause in the pending approval's snapshot, so charts of one request keep distinct, consecutive ids
  (see [`docs/ui/chart-from-json.md`](../ui/chart-from-json.md) §6.2).
- Chart frames without `chartId` remain valid.
- History replay keeps a stored `chartId` and never mints a new one.

```json
{
  "kind": "line",
  "chartId": "c1",
  "title": "currentDraw (BOS CellAging 01)",
  "x_label": "Time",
  "y_label": "currentDraw",
  "series": [
    {
      "name": "currentDraw",
      "x": ["2026-05-13T15:10:39Z", "2026-05-13T15:16:39Z"],
      "y": [0.99, 9.89]
    }
  ]
}
```

Where ids are assigned:

- `BuildChartFromTabularResultExecutor` assigns `chartId` on chart success, before
  `addPendingParlerChartBlock` (the agent drains a FIFO queue of pending chart payloads onto the Parler stream).
  The tool success JSON includes the emitted `chartId`.
- `ParlerChartWireSupport` assigns `chartId` when it builds a numeric-history chart on the live tool path. The
  `query_property_history` tool result does not expose that id to the model; `PropertyToolsExecutor` does not
  touch the chart counter.
- Numeric-history charts rebuilt from stored tool rows for history export omit `chartId` rather than minting
  one.
- When no chart is emitted, no `chartId` is returned.

`parler-ui/lib/types.js` declares the optional `chartId`; `parler-ui/lib/wireAdapter.js` preserves it.

## Intent mode

`build_chart_from_tabular_result` accepts either an explicit `kind` or an `intent`:

- **Explicit mode:** the caller supplies `kind` (`line`, `bar`, `scatter`, `pie`, `histogram`, `boxplot` or
  `heatmap`). `histogram` takes a `bin_numeric` result table and `boxplot` a `box_summary` result table, both
  without column bindings; `heatmap` takes a long table with `xColumn` = column dimension, `seriesColumn` = row
  dimension, `yColumn` = cell value.
- **Intent mode:** the caller supplies `intent` and no `kind`; Java selects `line`, `bar`, `scatter`,
  `histogram` (from a binned source), `boxplot` (from a box-summary source), or a fallback.
- `kind` and `intent` are mutually exclusive; supplying both returns `CHART_INVALID_PARAMETERS` and emits no
  chart.

### Intent values

The intent set is closed:

- `time_trend`
- `rank`
- `compare_groups`
- `correlation`
- `distribution`
- `status_timeline`
- `composition`

An unknown intent is an invalid call:

```json
{
  "status": "error",
  "code": "INTENT_UNKNOWN",
  "message": "intent must be one of: time_trend, rank, compare_groups, correlation, distribution, status_timeline, composition"
}
```

A known intent that cannot produce a chart for the given data returns a successful fallback, because it is a
product boundary rather than an invalid call:

```json
{
  "status": "success",
  "code": "CHART_FALLBACK",
  "requestedIntent": "status_timeline",
  "fallback": true,
  "fallbackReason": "STATUS_TIMELINE_NOT_SUPPORTED_IN_PHASE_1"
}
```

Fallback results do not include `chartId`. A successful intent-mode result:

```json
{
  "status": "success",
  "code": "CHART_EMITTED",
  "chartId": "c1",
  "requestedIntent": "rank",
  "selectedKind": "bar",
  "fallback": false,
  "sourceResolved": "cache_id",
  "pointCount": 12,
  "seriesCount": 1
}
```

Field values:

- `selectedKind`: `line` | `bar` | `scatter` | `histogram` | `boxplot`
- `requestedIntent`: one of the intent values above
- `fallback`: boolean
- `fallbackReason`: stable string: `STATUS_TIMELINE_NOT_SUPPORTED_IN_PHASE_1`, `INTENT_DATA_SHAPE_MISMATCH`, or
  `INTENT_SHAPE_NOT_SUPPORTED_IN_PHASE_1` (the `PHASE_1` suffix is part of the stable code)

`autoReason` and fallback fields stay in the tool result JSON; they are not added to `ChartBlock`.

### Decision table

| Intent | Required shape | Output | Otherwise |
|---|---|---|---|
| `time_trend` | datetime/numeric X + numeric Y, at least 2 points | `line` | fallback reason |
| `rank` | category + numeric metric | sorted `bar` | fallback reason |
| `compare_groups` | one categorical X plus one numeric metric, or an existing multi-series bar shape within the series cap | `bar` | fallback reason |
| `correlation` | numeric X + numeric Y | `scatter` | fallback reason |
| `distribution` | a `bin_numeric` result table (histogram) or a `box_summary` result table (boxplot) | `histogram` / `boxplot` by source shape | **error** `DISTRIBUTION_REQUIRES_BINNED_SOURCE` with a `recoveryHint` naming `bin_numeric` / `box_summary`; the tool never bins or summarises implicitly |
| `status_timeline` | state/event rows | no chart | `STATUS_TIMELINE_NOT_SUPPORTED_IN_PHASE_1` |
| `composition` | category + numeric metric | sorted `bar` | fallback reason |

Constraints:

- An intent/data mismatch falls back; `correlation` is never silently reinterpreted as `time_trend` or the
  reverse.
- `compare_groups` performs no pivoting or aggregation.
- Extra categorical (grouped-bar) axis detection for `compare_groups` uses **DataShape STRING column**
  metadata only; a shape that omits STRING typing can produce a false negative.
- Two categorical dimensions that would need grouped or stacked semantics return
  `INTENT_SHAPE_NOT_SUPPORTED_IN_PHASE_1`.
- Intents never select `pie`, `heatmap`, a horizontal bar or a stacked bar; those need explicit `kind` or the
  explicit bar parameters.
- An existing multi-series bar table can still be used when its series columns are compatible.

### Tool schema

- The root `parameters` JSON Schema is a single **`type: object`** with shared **`properties`** (`kind` and
  `intent` are optional fields on the same object). There is **no** root-level `oneOf` for the two modes: some
  providers reject that shape for the whole tools-bearing LLM request.
- **`required`** includes **`source`** and **`xColumn`**; mutual exclusion of **`kind`** and **`intent`** is
  stated in the tool description and enforced at **runtime** (invalid when both or neither are set).
- When **`source`** is **`cache_id`**, a non-blank **`cacheId`** is required **before** a phase-boundary
  **`status_timeline`** fallback can be returned (the same **`MISSING_CACHE_ID`** error as chart-emitting
  paths). Cache **existence** is not checked for that fallback, only the presence of **`cacheId`**.

### Implementation shape

- Source and table resolution is shared by explicit and intent modes (`TabularChartSourceResolver`).
- `ParlerTabularChartIntentResolver` holds the intent decisions; `ParlerTabularChartBuilder` builds the final
  `ChartBlock`.
- `TabularPasswordColumnGuard` blocks PASSWORD columns on every axis and series.

## Skill guidance

Skills describe visual intent, not fixed chart coordinates.

Preferred:

```markdown
For region comparisons, prefer a compact visual summary when useful:
- compare regions by issue category
- rank assets by severity when the user asks which needs attention first
- use trend charts only for time-window history questions
- use table-only output when the evidence is too sparse for a reliable chart
```

Avoid:

```markdown
Always build a bar chart with x=USA/Germany and y=Wrist3Temperature.
```

Region-health example:

```markdown
When enough tabular evidence exists, choose visualization by intent:
- `rank` for "which asset or region needs attention first"
- `compare_groups` for one metric compared across regions
- `time_trend` only when the user asks for history over a time window
- table-only output when the comparison uses prose evidence or unsupported dimensions
```

Skills may name domain concepts and required evidence; they should not fix chart coordinates.

## Tests

Tests assert structure, not prose:

- The routing text contains the neutral chart wording.
- `build_chart_from_tabular_result` success includes `chartId`, and the wire chart carries the same id.
- Numeric-history live charts get a `chartId`; history-export reconstruction omits it.
- History replay accepts chart frames without `chartId` and preserves a stored one.
- Fallback results contain no `chartId`.
- Explicit `kind` mode works; `kind` + `intent` together is an invalid-argument error.
- The tool schema uses a single root `type: object` (no root-only `oneOf`)
  (`BuildChartFromTabularResultToolSchemaTest`, `LlmJsonSchemaCompat`).
- Unknown intent returns `INTENT_UNKNOWN`; `time_trend` → `line`; `rank` → sorted `bar`; `correlation` →
  `scatter`; `composition` → sorted `bar` (`ParlerTabularChartIntentResolverCompositionTest`).
- Unsupported shapes return `CHART_FALLBACK` with a stable `fallbackReason`; mismatches fall back rather than
  changing intent.
- Protected columns stay blocked on all chart axes and series.

Each new chart kind updates the chart contract, UI validation, renderer, tests and export behavior together.
