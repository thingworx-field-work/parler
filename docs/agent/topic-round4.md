# Topic round 4 — a named unit establishes the document scope, and a multi-word signal is not a first-word trigger

Topic: `topic-round4`

## Fresh-thread implementation context

Before changing files, the agent MUST read repo-root `AGENTS.md` and `docs/review-framework.md`.

- **BUSINESS_CONTEXT:** A runtime user asks what to do or collect about a symptom on a unit they name ("`Demo_Unit_1` shows a pressure alarm; what should I collect?"). The method for that task exists as a generated topic in the unit's document set, and it is found only when the search runs inside the unit's document scope (round 3: the lane works only inside a real scope). Today the scope exists only after a `resolve_thing` result is in the conversation (or the host supplied a unit). A first message that merely names the unit does not create it: whether the model calls `resolve_thing` first is the model's choice. When it does not, the search runs unscoped, no topic is offered, and the model answers from general knowledge or from whatever document pages matched. A user should not have to ask an unrelated question first to make the product find the prepared method. A second, smaller defect sits in the same lane: a natural multi-word signal name turns its first word into a trigger for the whole topic.
- **CURRENT_IMPLEMENTATION:** `ConversationEntityScope` (`tools/`) derives the default scope from the newest successful single-match `resolve_thing` row in the message history (at turn start and at approval continuation, and in-turn after the tool runs), through `AgentThing.resolveEntityDocumentSet` (private) → the public `DocumentKnowledgeRuntime.resolveHostContextScope(agent, thingName)` (override-first, then the built-in matcher). Host context (`maybeInjectHostContextDocumentScope`) is the other injector and takes precedence. `DocumentKnowledgeRuntime.executeSearchDocumentChunks(call, agent)` is a public overload that delegates to a settings-based overload, which applies the injected scope as the default `documentIds` only when the model omitted that field, and which has early returns (empty input, unresolved index) before `searchIndex`. `searchIndex` labels the origin with a two-way test: `CONVERSATION` gives `conversation-entity-resolver` and anything else gives `host-context-resolver`. Offline tests reach only the settings overload, because the public one builds its settings from a platform agent. `search_document_chunks` accepts `assetContext` as "optional asset context such as asset model, component, or document type hints": every textual, numeric and nested value in it feeds **document scoring** (`SearchRequest.from` → `parseAssetContext` → `collectAssetContext`), and it never establishes scope. In the topic lane, `DocumentKnowledgeSearchScorer.structuredTopicEvidence` awards 25 when `queryTokenMatchesSignalName` matches a query token to a chunk signal name, and that helper accepts equality or a prefix in either direction when both sides have at least four characters. The lane's other phrase test, the 35-point heading term, needs the whole query inside the heading. Section 2 gives the verified facts.
- **TERMS_AND_CONTRACTS:** *Unit scope* is the injected default document list; *origin* is `AgentToolContext.DocumentScopeOrigin`; an *execution segment* is the span in which one `AgentToolContext` set-up lives (section 3, R16 "Lifetime"). The result field `documentScopeSource` names who injected a scope (`host-context-resolver`, `conversation-entity-resolver` and, new, `asset-context-resolver`). `warnings` in a search result is a priority field for the egress gateway; its aggregator is `DocumentKnowledgeWarnings`. No `CONTRACTS/*.md` file mentions `search_document_chunks`, `documentScopeSource` or `assetContext`, so no contract edit or `CONTRACT_VERSION.md` bump is expected. Section 10 is the glossary.

The unit's document set still needs a `ResolveDocumentSet` override or an exact `assetModels` match in the deployment (round 2 R6); nothing here changes that. A named unit counts only after it passes the same visible-Thing gate that scalar Thing tools use and resolves to a non-empty document set through the same resolver as every other scope source. ## 1 What this change is for

Round 3 made the topic row reach the model whenever the search runs inside a unit's document scope. The scope itself comes from the conversation: the newest successful single-match `resolve_thing` result, or host context. That leaves a gap at the very start of a conversation.

**The failing shape (reproducible on any synthetic package).** A fresh conversation, no host context. First message: "`Demo_Unit_1` shows a pressure alarm. What should I collect for the ticket?" The model may call `resolve_thing` first, or may go straight to `search_document_chunks` with `{"query": "...", "assetContext": {"thingName": "Demo_Unit_1", ...}}`. In the second case the search has no `documentIds` and no injected scope, runs with `selectionMode` `diversified`, returns no `topics`, and the unit's prepared method never reaches the model, although the model itself supplied the unit's exact name. The same question after a `resolve_thing` turn runs as `documentIds-filter` and offers the topic. In live sessions of one deployment the model took the first path in repeated attempts of that exact first message and the second path in others; the choice is not deterministic, and the existing guidance ("call resolve_thing only when the unit is not yet established or has changed" in `llm_tool_routing_guide.txt`, restated in `LLM_CONTEXT.md` as "not established or has changed") did not prevent it. A text-only guidance change is therefore not a fix; it can still be an aid.

**What this round guarantees, and what it does not.** When the model's search carries a usable unit name, the first search is scoped. It does **not** solve a first message where the model supplies no name at all, a later search or turn that does not name the unit again, or an approval pause (R16 "Lifetime").

The second defect is separate and smaller. The topic lane's `structuredTopicEvidence` gives 25 points when a query token matches a chunk signal name by `queryTokenMatchesSignalName`, which accepts a prefix in either direction when both strings have at least four characters. The signal `pump shows low pressure` is matched by the query token `pump`, so a question about priming a pump can fire a topic about a low-pressure condition from its first word alone (25 plus up to 20 weak points passes the floor of 30). Authors can avoid it by choosing signals whose first word is specific; that is a workaround for a rule that should not make a natural multi-word phrase a first-word trigger.

### In scope (round 4)

- **R16** A search that names a unit in `assetContext.thingName` and has no scope otherwise establishes that unit's document scope for the current execution segment, after validation.
- **R17** A search whose eligible unit name did not establish scope says so in one warning, whose wording follows the stage that failed.
- **R18** In the topic lane only, a query token matches a signal name by prefix only when the signal name is a single token under the lane's tokenizer. A multi-word signal name matches as a whole: by full-name equality with a request signal, as today, or when every one of its tokens is in the query.
- **R19** Two `features` names so that an installation's behaviour is observable.

### Out of scope (do not do these)

- Refusing, blocking or rewriting an unscoped search. Unscoped document search is legitimate for agents and questions that name no unit (documentation Q&A, a manual lookup, an unknown unit).
- Forcing or inserting a property read, a `resolve_thing` call, or any other tool call; rewriting the model's tool list for the turn.
- Treating any `assetContext` field other than an exactly named, visible, document-bearing `thingName` as an identity, or removing any existing scoring effect of an `assetContext` value. `assetModel`, `component`, `documentTypes` hints keep their scoring-only meaning, and `thingName` keeps contributing to scoring as it does today.
- Mining the user's message for unit names (n-gram or token linking), turn-start probes, a stored "current unit" field, a synthetic history row, or restoring the derived scope after an approval pause or in a later turn (section 4, rows 3 and 4).
- Changing host-context precedence, the explicit `documentIds` rule, the `ConversationEntityScope` history rule, document or topic ranking, embeddings, topic execution order, the mixed document-plus-action gap, or egress limits. Beyond R18, topic ranking does not change.
- Handling a unit change inside a conversation by `assetContext` (a changed unit still needs `resolve_thing`; section 4, row 5).
- In-runtime identity rules (display name, serial, suffix) for `thingName`.

## 2 Verified facts this design relies on

All read at the shipped tree (`nearterm`, agent 0.1.253).

1. **Scope sources and precedence.** `AgentToolContext` holds a thread-local injected scope (`documentIds`, `resolverSource`, `DocumentScopeOrigin` ∈ {`HOST_CONTEXT`, `CONVERSATION`}). `ConversationEntityScope.injectFromHistory` does nothing when a scope is already injected; `afterResolveThing` replaces or clears any non-host scope and never touches a host one. `DocumentKnowledgeRuntime.executeSearchDocumentChunks(call, settings, agentName)` defaults `documentIds` to the injected list only when the arguments have no `documentIds` field, and then `searchIndex` adds `documentScopeResolverSource` and `documentScopeSource` to the result. That mapping tests only for `CONVERSATION` and sends everything else to `host-context-resolver`, so a third origin is reported as host context until the mapping is extended (R16).
2. **How the unit's documents are found.** `DocumentKnowledgeRuntime.resolveHostContextScope(agent, key)` is public: it needs document-knowledge built-ins enabled, a configured repository and a resolved index, then `resolveDocumentSetResult(index, key, customResolverFor(agent))`; it returns empty on any problem or an empty set. `AgentThing.resolveEntityDocumentSet` (private) only calls it. Every scope source ends here, so an unknown or unbound name yields no scope.
3. **The visible-Thing gate.** `ScalarThingnamePreflight.gateApplicationThing(parameterName, rawName)` trims, requires non-blank, resolves a Thing the effective principal can see (`EntityUtilities.findEntity`, the precedent used by `discover_thing_members`), and returns an `ApplicationThingGateOutcome` with public fields `thing`, `canonicalThingName` and `errorJson` (null on success). Its constructor is private and a successful production outcome holds a platform `Thing`; the test seams (`modelVisibleThingNamePredicateForTests`, `resolveVisibleThingOverrideForTests`, `gateCanonicalThingNameOverrideForTests`) cannot produce one without a platform `Thing`. It does not use identity rules (display name, serial, suffix); those are `resolve_thing`'s. Whether a different spelling (for example another letter case) resolves is decided by that lookup, not by this design.
4. **Entry points.** The registry executes `search_document_chunks` through `DocumentKnowledgeToolsExecutor.executeSearchDocumentChunks(call)`, which calls `DocumentKnowledgeRuntime.executeSearchDocumentChunks(call, AgentToolContext.getAgentThing())`. That overload has the agent, runs before the scope-defaulting block, and can wrap whatever the settings overload returns, including its early returns.
5. **The lane needs a scope.** `DocumentKnowledgeSearchScorer.topicLane` returns an empty list when the request's effective `documentIds` is empty. It does not look at which ids a result later displays. A lane candidate must also be inside any injected scope (`isLaneCandidate`), so explicit ids outside an injected scope give an empty lane, and `load_topic` refuses a document outside it (`TOPIC_OUT_OF_SCOPE`).
6. **A displayed id list is not the search domain.** `ToolResultEgressGateway` samples ordinary arrays to 20 and can set `sampleOnly`; `selectedDocIds` in a result can therefore be a 20-id view. At this tree `buildSelectionPlan` with no `documentIds` selects every available document for `diversified`. Tests and diagnostics MUST NOT infer from a short `selectedDocIds` that a document was not searched.
7. **Asset context already scores.** `SearchRequest.from` collects every textual, numeric and nested value of `assetContext`, including `thingName`, into asset-context tokens and phrases used by document scoring. A failed or skipped derivation therefore still leaves that scoring in place, and an `assetModel` or unresolved `thingName` can change scores, selected documents or returned matches without establishing scope.
8. **The assetContext schema text** is "Optional asset context such as asset model, component, or document type hints." (`DocumentKnowledgeToolSchemas`, also copied in `docs/agent/document-chunk-tools.md` and `docs/agent/all-tools.md`).
9. **The lane rule.** `TOPIC_LANE_FLOOR = 30`, `TOPIC_LANE_MIN_STRUCTURED = 25`, `TOPIC_LANE_WEAK_CAP = 20`, `TOPIC_LANE_MAX = 2`. Request-signal equality is 50 per matching signal; a token/signal match is 25 per query token; a tag needs every tag token in the request tokens (25); a heading containing the whole multi-token query is 35. `tokenize` lower-cases, splits on anything outside `a-z0-9`, drops parts shorter than 2, and returns the whole trimmed text as one token when nothing survives (a query or signal entirely in Chinese, for example).
10. **Context lifetime.** The running loop clears `AgentToolContext` when a chat turn or a continuation ends (`AgentThing` `finally` blocks around `AgentToolContext.clear()`). After a gated tool's approval, `runParlerPostToolAgentLoop` binds a continuation and calls `maybeInjectConversationEntityDocumentScope(messages)`, which derives only from `resolve_thing` rows in the history. A search-only first message has no such row.
11. **What offline tests can reach.** `DocumentKnowledgeSettings.fromAgent(null)` returns the defaults, so the public overload with a null agent returns `DOCUMENT_REPOSITORY_NOT_CONFIGURED` and never reads a fixture (run on this tree). The test classpath has no mocking library and cannot construct a platform `Thing` or agent. Every existing fixture search calls the settings overload `executeSearchDocumentChunks(call, TopicTestFixtures.SETTINGS, TopicTestFixtures.AGENT)`, including the `execute` function that `TopicOfferFlowTest` gives its scripted loop.
12. **Tool admission reads the scope, but R16 cannot change it.** `resolveToolAdmissionSignals` reports `documentScopeActive` on each round. `ToolAdmissionPolicy.documentSignal` is consulted only in `narrow`, where document tools are not advertised without a document signal, so a search that runs there already had one. `lazy` does not consult it (`coreToolNames`) and the default `off` passes everything through. R16 therefore adds or removes no tool.
13. **`resolve_thing` can be advertised and still be useless.** It is in the always-advertised core set, but it needs at least one loaded v3 identity rule. `ScalarThingnamePreflight.resolveThingRecoverableThisTurn()` (package-private, with the test override `resolveThingRecoverableOverrideForTests`) reports this, and `identityResolutionRequiredJson` already words its recovery text differently on that basis.
14. **The empty-input return cannot meet an eligible search.** `isEmptySearchInput` is false for any non-empty `assetContext` object, so among the early returns only `resolveFailureSearch` can apply to a search with a usable `thingName`.

## 3 Required behaviour

### R16 A named unit establishes the document scope

**Eligibility to attempt.** `DocumentKnowledgeRuntime.searchWithUnitScope` runs `SearchUnitScope.derive(call, canonicalName, resolver)` before it delegates to the settings overload. A search is **eligible** when all hold:

1. the call's arguments have **no `documentIds` field** (an explicit value, including `[]`, always wins, as today);
2. **no scope is injected** (`AgentToolContext.getInjectedDocumentScopeIds()` is null or empty; host context and a scope from `resolve_thing` are therefore never touched);
3. `assetContext` is an object whose `thingName` is a **textual, non-blank** value.

Anything else is silent: nothing is derived, nothing is added to the result.

**Validation of an eligible search.** The supplied value is trimmed and must then (a) be at most 256 characters with no control characters, (b) pass the canonical-name decision (production: `ScalarThingnamePreflight.gateApplicationThing("assetContext.thingName", value)` succeeded, adapted to its `canonicalThingName`), and (c) resolve to a **non-empty** document set through the resolver (production: `DocumentKnowledgeRuntime.resolveHostContextScope(agent, canonicalName)`, called directly). Failing any step is a **rejected eligible name** (R17). Steps (a) and (b) are the **identity stage**; step (c) is the **document stage**, reached only with a canonical name.

**Injected decisions (the seam).** `SearchUnitScope.derive` takes `Function<String, Optional<String>> canonicalName` (the gate as a decision: the canonical Thing name or empty) and `Function<String, Optional<ResolvedDocumentSet>> resolver`. Both reach it through one package-private entry point, because the public overload cannot read a fixture offline (section 2 item 11):

```java
public static String executeSearchDocumentChunks(ToolCall call, AgentBaseThing agent) throws Exception {
    DocumentKnowledgeSettings settings = DocumentKnowledgeSettings.fromAgent(agent);
    String agentName = agent != null ? agent.getName() : "";
    if (agent == null) {
        return executeSearchDocumentChunks(call, settings, agentName);
    }
    return searchWithUnitScope(call, settings, agentName, SearchUnitScope::visibleCanonicalName,
            name -> resolveHostContextScope(agent, name));
}

static String searchWithUnitScope(ToolCall call, DocumentKnowledgeSettings settings, String agentName,
        Function<String, Optional<String>> canonicalName,
        Function<String, Optional<ResolvedDocumentSet>> resolver) throws Exception {
    SearchUnitScope.Outcome outcome = SearchUnitScope.derive(call, canonicalName, resolver);
    return SearchUnitScope.appendWarning(executeSearchDocumentChunks(call, settings, agentName), outcome);
}
```

The settings overload stays exactly as it is, so it remains the baseline for every "unchanged" test. Tests call `searchWithUnitScope` with fixture settings and plain lambdas. No test hook is added: `SearchUnitScope` holds no mutable static state. `visibleCanonicalName` is the adapter over `ScalarThingnamePreflight.gateApplicationThing`; its negative path is testable through `modelVisibleThingNamePredicateForTests`, and its positive path needs a platform `Thing`, so it is covered by the User's live check (section 8 item 1).

**Result of the derivation.** `derive` returns a small outcome object (not a thread-local, not a stored field) that holds the optional R17 warning. On success it calls `AgentToolContext.setInjectedDocumentScope(ids, source.wire(), DocumentScopeOrigin.SEARCH_ASSET_CONTEXT)` (a third enum value) **before** delegating, so the settings overload defaults `documentIds` to that set exactly as for any injected scope and the topic lane runs in this very search. The result reports `documentScopeSource` = **`asset-context-resolver`** for this origin (extend the existing two-way mapping in `searchIndex`) and the usual `documentScopeResolverSource`. `searchWithUnitScope` then appends the outcome's warning to the returned JSON text once (R17). Each attempt on an eligible name logs one info line with the sanitized name, the document count and the resolver source or the rejection step, as `ConversationEntityScope` does, so a missing binding can be told apart from a defect.

**Lifetime.** The derived scope lasts for the **current execution segment**: from the search that established it until `AgentToolContext` is cleared, which ends the chat turn or the continuation that was running. Within the segment later searches default to it, a later successful `resolve_thing` replaces it and a non-single-match one clears it, as for a conversation scope (`afterResolveThing` already treats any non-host scope that way; add nothing there). It is **not** restored after an approval pause, because the continuation's re-derivation reads only `resolve_thing` rows (section 2 item 10), nor in a later user turn. A new segment is scoped again by a search that names the unit again, or by `resolve_thing`. Loaded methods and the approved tool call are unaffected by the absence of the derived scope. Restoring it would need a stated source and its own acceptance case; it is deferred (section 4, rows 3 and 4). This limit applies to scope that came **only** from R16: a successful `resolve_thing` already in the history still scopes later turns and continuations without the unit being named again.

**Model-facing text.** Replace the `assetContext` property description in `DocumentKnowledgeToolSchemas` with exactly: `Optional asset context such as asset model, component, or document type hints. To scope searches in this step to one unit's documents, put that unit's canonical Thing name in thingName; it is used only if it names a visible unit that has documents. To keep a unit across the conversation, call resolve_thing.` Update the two prose copies named in section 7.

**Existing scoring is untouched.** The `assetContext` value, including `thingName`, keeps feeding `SearchRequest.from`'s asset-context scoring in every case, successful derivation or not.

**Fail open.** Any exception, an unresolved index, or a negative decision leaves the arguments, the injected scope and the result exactly as they are before this round (apart from R17's warning on a rejected eligible name). A null agent skips the derivation entirely: no attempt and no warning. `derive` parses the arguments itself and treats unparsable or non-object arguments as not eligible, so the settings overload then fails on them exactly as it does today. A settings-overload failure after a successful derivation leaves the scope set for the segment, which is harmless because the scope was already validated. The derivation never changes a tool result's matches except through the scope a successful derivation injects.

### R17 A rejected eligible name says so

When an eligible search's name was rejected, the outcome carries **one** warning, appended once to the returned JSON of that call. All forms have the code `UNIT_SCOPE_NOT_ESTABLISHED`. The stage that failed selects the message, and `derive` already knows it:

| Stage that failed | When | `message` |
| --- | --- | --- |
| Identity, `resolve_thing` can help | Step (a) or (b) failed, including an exception in the canonical-name decision, and `ScalarThingnamePreflight.resolveThingRecoverableThisTurn()` is true | `assetContext.thingName '<value>' did not establish a document scope: it is not the exact name of a visible unit. If the user named a unit, call resolve_thing with the user's text and search again; otherwise ignore this.` |
| Identity, `resolve_thing` cannot help | The same failures, and that check is false (section 2 item 13) | `assetContext.thingName '<value>' did not establish a document scope: it is not the exact name of a visible unit. Use the exact Thing name if the user named a unit; otherwise ignore this.` |
| Document | Step (c) failed after a canonical name was accepted: an empty set, an exception in the resolver, or an unresolved index | `assetContext.thingName '<value>' is a visible unit, but no document scope is available for it (no documents for it, or document knowledge unavailable). This search is not limited to that unit's documents. Looking the unit up again will not change this.` |

An identity lookup can repair only the identity stage: `ConversationEntityScope.afterResolveThing` ends in the same document resolver, so after a document-stage failure `resolve_thing` would succeed, leave no scope, and the next search would warn again. The document form therefore never directs another lookup. `resolveThingRecoverableThisTurn()` says only that identity rules are loaded, so it is consulted only at the identity stage. The production resolver turns an unresolved index and any exception into an empty result, so those cases cannot be told apart from a missing binding; the message names both, and the search's own `DOCUMENT_REPOSITORY_*` or `DOCUMENT_TOOL_INTERNAL_ERROR` warning sits beside it when the index is the cause.

`<value>` is the trimmed supplied text with control characters replaced by spaces and cut to 80 characters, never between the two halves of a surrogate pair (so a value that fails (a) still reaches this warning, sanitized). The entry is an object with exactly `code` and `message` (the shape of `DocumentKnowledgeWarnings.toJsonList` entries without a `count`, and of the private `warning(code, message)` helper in `DocumentKnowledgeRuntime`; build it in `SearchUnitScope` and do not widen that private helper's visibility). Because the settings overload can return `resolveFailureSearch` before `searchIndex` (section 2 item 14), the append is a small post-processing step on the returned JSON text, in `SearchUnitScope.appendWarning`: parse, add the entry to the `warnings` array (create it if absent) unless an entry with that code is already there, and write it back; on any parse failure return the text unchanged. Nothing is added when the search was not eligible (no `thingName`, a blank or non-text `thingName`, a scope already injected, or `documentIds` supplied), when the agent is null, nor when derivation succeeded. `warnings` is a priority field and survives egress. This is the only text-level aid: where identity is the problem it names the already existing, stateful, validated anchor (`resolve_thing`) at the moment the model has shown it knows a unit name. It can be dropped without affecting R16 (section 9).

### R18 A multi-word signal is not a first-word trigger (topic lane only)

In `structuredTopicEvidence` only, two changes replace the 25-point token/signal test.

**Single-token signals.** The loop over query tokens calls a lane-local helper `laneTokenMatchesSignalName(token, signalName)`. It applies `queryTokenMatchesSignalName` (equality, or the length-qualified prefix in either direction) only when `tokenize(signalName).size() == 1`, and is false for any other signal. The query-token guard `!assetTokens.contains(token)` stays on that loop.

**Multi-word signals.** A new branch takes the chunk's signals that tokenize to two or more tokens, after the existing identity filter, de-duplicated by their token list, and adds **25 once for each** whose tokens are all in the distinct query tokens (`queryTokens.containsAll(tokens)`). This is the shape of the existing tag rule, on query tokens only: a request signal's tokens do not count here. `chunkSignals` already excludes a signal made only of asset tokens (`isIdentityOnly`), so the branch needs no second asset test, and a multi-word signal with at least one task word can qualify when the query has all of its words. Token order does not matter.

`queryTokenMatchesSignalName` and its other callers (the manual ranker, line ~550) are **unchanged**. Request-signal equality (`signal::equalsIgnoreCase`), tag token-set matching, the heading phrase test, the weak-text cap and the floor are unchanged. A signal or query entirely outside `a-z0-9` tokenizes to one token (the whole text), so a non-Latin signal behaves as before.

**Consequence, stated for authors.** A multi-word signal fires when the query contains all of its words, or from a request signal equal to the name, a tag, or the heading phrase; its first word alone earns nothing. Matching is by exact token with no stemming, so `showing` does not satisfy `shows`: an author wanting a looser match adds a tag or a shorter signal. Common words carry a small risk that a multi-word signal matches an unrelated query, but 25 is below the floor of 30, so it still needs weak evidence and is accepted as such. The generator's advisory about first-word prefixes describes the old rule; it is the external generator's to reword when `topic-signal-exact/1` is installed.

**Single-token test, precisely.** `tokenize` drops parts shorter than two characters and everything outside `a-z0-9`, so `valve A` and `PUMP 压力低` each tokenize to one token and keep the prefix rule, unchanged. Such a name has only one Latin word that can be matched, so it behaves like the signal `pump`. A tag still needs five weak points to reach the floor: a tag alone earns 25, and the floor is 30.

**Measured consequence.** The rule was applied to a throwaway copy of the shipped tree and the lane was run with the signal `pump shows low pressure`, the only signal on the topic unless a row says otherwise. `Q` is the query `pump shows low pressure what should I collect`.

## 9 Decisions proposed for reviewer agreement, and what is deferred

- **Derive at search time from the name the model already supplies, after the gate and a non-empty document set**, rather than any of the alternatives below. It reuses one resolver and one visibility gate, adds no state and no model-visible tool change beyond one sentence, and fixes the first search of a conversation, which is where the failure occurs. A real, visible, documented unit named by mistake is the same selection error as `resolve_thing` on that unit; no further confirmation is added.
- **Segment lifetime, explicit.** The derived scope lasts for the current execution segment and is not restored after an approval pause or in a later turn; the guarantee is conditional on the search carrying a usable name. This is the smallest change that fixes the first search; persistence is a separate design with its own source and test.
- **Alternatives rejected.** (a) *Guidance only*: the guidance already exists and did not hold in repeated live attempts; kept as an aid (the schema sentence, one sentence in the guides). (b) *Mining the user message for unit names* at turn start: false-positive risk against ordinary words, needs identity rules over n-grams, and treats text as identity; deferred. (c) *Refusing unscoped search* or forcing `resolve_thing`/a property read: breaks legitimate unscoped use and changes the product experience the wrong way. (d) *Running `resolve_thing`'s identity rules in the runtime on `assetContext.thingName`*: wider reach (display names, serials, suffixes) but a larger surface and a second identity path; deferred; R17 points the model to `resolve_thing` instead. (e) *Storing the derived unit or writing a synthetic `resolve_thing` row* so later turns and approval continuations stay scoped: new state and a persistence question; deferred. (f) *Treating every `assetContext` field as identity*: rejected; only an exact visible, document-bearing `thingName` counts.
- **R17 is separable, and its wording follows the failed stage.** If a reviewer judges the warning an unnecessary model-facing text, drop R17 and P22 with no effect on R16; section 4 rows 8 and 9 then have no recovery hint. A single recovery sentence is rejected: identity lookup cannot repair a missing binding or an unavailable repository, because it ends in the same resolver. No retry state is added; the derivation already knows the stage.
- **The prefix rule is lane-local** so the manual ranker's results do not move.
- **A multi-word signal is matched as a whole.** Removing the prefix rule alone would stop a query that states the whole signal from offering the topic (it scored 33 to 45 today and would earn nothing), because the heading phrase test needs the whole query inside the heading and a request signal helps only when it equals the authored name exactly. R16 exists to reach the method on the first question, so that is not acceptable. The token-set branch keeps that reach and removes the first-word trigger. It reuses the shape of the tag rule and adds no floor, cap or tokenizer change. Stemming, partial matches and weights per signal word are rejected as wider changes. The feature name `topic-signal-exact/1` still fits: a first word alone is no trigger.
- **The test seam is an entry point, not hooks.** Test hooks that replace the two decisions would not be enough, because the public overload reads no fixture offline (section 2 item 11). One package-private method covers P19 to P28 with no static state.
- **No version bump rule, no setting.** Both behaviours are on whenever the extension carries them; `features` makes that observable.
- **Deferred:** stored or synthetic-row unit persistence across turns and approval pauses; unit change by `assetContext`; identity-rule resolution inside the runtime; text mining; the mixed document-plus-action gap; CJK-aware tokenization; any change to topic execution, or to ranking beyond R18.

## 10 Glossary

- **unit scope** — the injected default `documentIds` list derived from a named unit; it narrows a search and never creates one.
- **origin** — `HOST_CONTEXT`, `CONVERSATION` (from a `resolve_thing` row) or, new, `SEARCH_ASSET_CONTEXT` (from a search's `assetContext.thingName`).
- **eligible search** — no `documentIds` field, no injected scope, and a textual non-blank `assetContext.thingName`.
- **identity stage, document stage** — the two parts of validating an eligible name (R16): whether it is an acceptable canonical Thing name, then whether that unit has a document set. R17's wording follows the stage that failed.
- **named unit** — an eligible search's `thingName` that passes validation: at most 256 characters without control characters, the canonical-name decision, and a non-empty document set.
- **execution segment** — the span during which one `AgentToolContext` set-up lives: a chat turn, or the continuation after an approval; it ends when the context is cleared.
- **topic lane** — the top-level `topics` array of a search result (round 3).
- **single-token signal** — a signal name for which `tokenize` returns exactly one token (including the whole text of a non-Latin name, and a name with one Latin word beside parts `tokenize` drops).
- **multi-word signal** — a signal name for which `tokenize` returns two or more tokens; in the lane it matches as a whole (R18).
- **request signal** — a signal object sent in the search request's `signals[]`; equality with a chunk signal name earns 50 in the lane.
