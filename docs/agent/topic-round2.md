## 1 What this change is for

Round 1 made a loaded method work: after `load_topic` the registered tools stay visible, the text stays in the request, and recognition survives an approval. The first run of a real conversation in the Parler interface never got that far. The method was not loaded, and nothing in the runtime made it likely to be.

The failing conversation (synthetic version): turn 1 names a unit and asks a property question; the model calls `resolve_thing` and answers. Turn 2 asks what to collect for a symptom on that unit and to collect it from the unit. The model's first tool of turn 2 is `search_document_chunks`, **not scoped** (the model passed a query, a symptom signal and an asset hint, but no `documentIds`; the unit's document set was never resolved). The top three hits are sections of large manuals; the topic chunk of the small article is not among them. The model reads the article's first page, then answers that it has no tool to collect from the unit. The registered log tools were not available to it: after the search, document-turn narrowing (round 1, section 2.6) left it five document tools, and only a loaded method lifts that.

Three separate causes, each with a class-level fix:

1. **The entity never became a document scope.** The product premise is a funnel: the trigger names one unit, the unit determines the document set, the set contains the topic. The runtime does the second step when a host context binds a Thing (`maybeInjectHostContextDocumentScope`), but not when the unit is only named in the conversation and resolved by `resolve_thing`. Scoped search finds the topic: in earlier runs with a document filter the topic was the first hit.
2. **A method on offer does not keep the tools.** Narrowing treats a search that returned a topic exactly like a search that returned manual pages. The model sees a topic it may not load, and the tools that its steps would use are gone.
3. **A hit does not say how it is used.** Of the model's decisions, whether to load a top-ranked topic is the one the runtime can make more likely at no cost, by saying so in the hit.

### In scope (round 2)

- **R6** Conversation entity scope: derive the default document scope from a resolved unit when no host-context scope was injected.
- **R7** Topic offer: a search result that contains a `contentType: "topic"` match lifts document-turn narrowing for the rest of the turn.
- **R8** A topic match carries `loadWith: "load_topic"`.
- **R9** One routing-guide sentence: for a request to collect or do something about a symptom on a named unit, use the unit already resolved in the conversation (resolve it only when it is not yet established or has changed) and search its documents before calling operational tools.
- **R10** Two additive `features` names.

### Out of scope (do not do these)

Changing search ranking, `CONTENT_TYPE_RANK`, `limit` defaults or document selection (§8 says when to reopen); a turn-start automatic topic search that the model did not ask for; per-topic tool admission; changing the round-1 active-method, retention or approval rules; durable entity memory beyond what the conversation history already holds; making scope a hard filter (it stays a default that an explicit `documentIds` suppresses); any UI or wire change; any new setting; version or changelog edits on the topic branch.

## 2 Background added for round 2

### 2.1 Where the document scope comes from today

`AgentToolContext.setInjectedDocumentScope(ids, source)` stores ThreadLocals, cleared per turn. The only caller is `AgentThing.maybeInjectHostContextDocumentScope(prep)` (three entry sites: `Chat`, `ChatAsync`, the gateway, right after `AgentToolContext.setHostContextJson`/`setAgentThing`). It requires an accepted, registered host context with `context.thingName`, then calls `DocumentKnowledgeRuntime.resolveHostContextScope(agent, thingName)` (override-first, then the built-in matcher over the index's manifests) and stores the result. It fails open. `search_document_chunks` uses the stored ids as the **default** `documentIds` only when the model omitted the field; `get_document_chunk` does not consult it; `load_topic` refuses a topic outside an injected scope (`TOPIC_OUT_OF_SCOPE`). `AgentThing.admissionSignals` also reads it (`documentScopeActive`). An approval continuation (`runParlerPostToolAgentLoop`) does not inject a scope today.

The normal two-turn path reuses the conversation's `ChatMessage` transcript as `messages`; tool results are `TOOL` rows carrying `executedToolName`, and an approval's `PendingApprovalRecord.messagesCopy` copies those rows. A row that existing history trimming has already removed is not available to anything derived from the transcript.

A conversation with no host context (the document-knowledge test method names the unit in turn 1 and says "this analyzer" afterwards) therefore has no scope unless the model calls `resolve_document_set` itself and passes the ids.

**The resolver needs configuration.** `resolveHostContextScope(agent, key)` first invokes the agent's overridable `ResolveDocumentSet(key)` service as the current user. The Java default returns an empty table. It then falls back to `DocumentSetResolver.resolveDefault`, which matches the key by **normalized exact equality** (trimmed, whitespace collapsed, lowercased) against a manifest's `documentProfile.assetModels[]`/`assetModels[]` entries. A Thing name that is neither mapped by an override nor equal to an `assetModels` entry resolves to `default-empty`, which `resolveHostContextScope` returns as no scope. R6 passes a Thing name, so R6 has this same precondition, and it is a precondition of the live check (§7), not something this round changes. The method also returns empty when `isDocumentKnowledgeBuiltinsEnabled()` is false or no repository is configured, which is how R6 stays inert on agents without document tools.

**Diagnostics.** When the default applies, `searchIndex` adds `documentScopeSource: "host-context-resolver"` and `documentScopeResolverSource` (the `custom` or `default-match` value) to the search result. The first label is a constant today, so R6 has to change it (R6 step 5).

**Admission.** `AgentThing.resolveToolAdmissionSignals` reads the injected ids on every round as `documentScopeActive`, and `ToolAdmissionPolicy.documentSignal` admits the `DOCUMENTS` bucket on it in `narrow` and `lazy` modes. In the default `off` mode the signal has no effect.

### 2.2 What `resolve_thing` returns

A successful single resolution is JSON of this shape (synthetic names): `{"status":"success","resultKind":"THING_RESOLVED_INLINE","totalCount":1,"matches":[{"name":"Demo_Unit_1","criticalProperties":{},"matchedBy":{...}}]}`. `resolve_thing` is outside `DocumentTurnToolNarrowing.NARROWED_TOOL_NAMES`, so a successful call sets the non-document latch and switches narrowing off for the rest of the turn. That is why conversations that call it before the first search never met the defect, and why one that resolved the unit in an earlier turn does.

An ambiguous result is `{"status":"error","code":"IDENTITY_AMBIGUOUS",...,"candidates":[...]}`, with no `matches`. A large result is `status: "success"` with `resultKind: "THING_RESOLVED_LARGE"`. A not-found result is an error envelope.

### 2.3 Search match construction

`DocumentKnowledgeRuntime.buildSearchMatch` builds each match as an ordered map (`docId, chunkId, heading, sectionPath, contentType, pageStart, pageEnd, score, bm25Boost, snippet, sourceLinks`). Search results pass through `ToolResultEgressGateway` by shape (round 1, section 2.7); an extra short string field does not change the compaction outcome of a typical result. Sampling keeps whole array elements, so a surviving topic match keeps `loadWith`.

`buildSearchMatch` is static and has no tool registry. `BuiltInTools.registerAll` registers `load_topic` and `search_document_chunks` under the same `documentKnowledgeBuiltinsEnabled` branch, so whenever the Java search runs, the Java loader is registered in the same registry. `search_document_chunks` also reaches `DocumentKnowledgeRuntime` only through that registration.

### 2.4 Post-tool hooks

Round 1's `taskstate/ActiveMethodHooks` is called from the same dispatch sites as `TaskProgressV1bDynamicMerge.afterGetAgentSkill`. New recognition in this round follows that pattern: independent of checklist code, called only on the Java built-in dispatch path, never after a same-named extended tool. Hooks differ in what they read: R6's reads every executed `resolve_thing` result (including error envelopes), R7's reads the search JSON, round 1's `afterLoadTopic` requires a success header. The built-in call site is the `_toolRegistry.executeTool` block in `AgentThing.dispatchExecuteToolCallWithoutRepetitionGuard`. A call stopped by `ConsecutiveIdenticalToolCallTracker` never reaches it.

### 2.5 Why a `resolve_thing` row survives to the next turn

R6 depends on the row being intact in `messages` at the next turn, so these facts were checked against the code.

- The in-memory `_conversations` list is the source of `messages` while the JVM holds the conversation. `AgentLoop.appendCompactedExecutedToolResultToMessages` appends the row with `executedToolName` set to the tool name, after egress.
- A conversation rebuilt from its Stream after a restart or eviction (`AgentConversationRehydrator`) has no `Role.TOOL` rows, so it has no derived scope until the model resolves again. That matches the rule that nothing new is stored.
- Egress keeps the JSON keys of a normal result: a small single-match result is unchanged or only has long strings excerpted. An oversized result can be wrapped, which fails validation and yields no scope.
- Several compaction paths replace a row through the two-argument `ChatMessage.toolResult`, which **drops** `executedToolName`: `LlmToolResultMatrixSealer`, `LlmToolResultCohortMerger` and `LlmToolResultTierBPromoter`. None of them touches a `resolve_thing` result. The sealer requires an eligible `resultKind` and `columns`; the cohort merger handles only `get_property_values` and the alert tools; Tier B promotes only already-sealed, cohort and entity-metadata formats.
- Rows for calls that did not run come from these producers, and all but the last keep the tool name: the `AgentLoop` cancel synthetics, `AgentLoop.appendRepositoryUnavailableSkippedSiblings`, `HitlSyntheticToolResultAppender.appendInterruptedSiblingsDurable`, and `PlaybookTerminalHandoff.appendSkippedSiblingToolResults`. The last builds its row with the two-argument overload, so its `executedToolName` is null. R6 step 1 corrects it. The remaining `HitlSyntheticToolResultAppender.appendDurable` callers write the row for the gated call itself, which is never `resolve_thing`.
- `ContextBudgetPlanner` materializes the outbound request and does not remove rows from `messages`. `ConversationsStorageBudgetTrimmer` and an installed conversation checkpoint can remove old rows; those conversations have no derived scope until the model resolves again.
- Tool calls in `AgentLoop` run on the turn's thread, so the `AgentToolContext` ThreadLocals written by a hook are visible to the next call.

## 3 Required behaviour

### R6 Conversation entity scope

Add a small class `tools/ConversationEntityScope` and one method `AgentThing.maybeInjectConversationEntityDocumentScope(List<ChatMessage> messages)` called at the three entry sites immediately after `maybeInjectHostContextDocumentScope`, only when no scope was injected (`AgentToolContext.getInjectedDocumentScopeIds()` null or empty). The class takes the resolver as a function argument (`String -> Optional<ResolvedDocumentSet>`), so it is testable without a ThingWorx runtime; the `AgentThing` methods only pass `key -> DocumentKnowledgeRuntime.resolveHostContextScope(this, key)`.

1. **Select, then validate.** Select the newest `TOOL` message in `messages` whose `executedToolName` is `resolve_thing`, **whatever its status**. Then validate that one row: it parses as a JSON object with `status: "success"`, `resultKind: "THING_RESOLVED_INLINE"`, `totalCount: 1` and exactly one entry in `matches[]` with a non-blank `name`. Anything else (error or ambiguity envelope, zero matches, `THING_RESOLVED_LARGE`, any other kind, unparsable) yields no scope. Never fall back to an older row: a newer ambiguous or failed result clears the entity. A row for a call that did not run (repetition block, skipped sibling, cancel synthetic, interrupted sibling) carries the tool name, so it also counts as a newest result with no scope; the model resolves again. When one batch resolves two units, the later row is the newest and its unit wins.

   **Tool identity on unexecuted calls.** The rule above depends on that name. Without it, a batch of `start_playbook` followed by `resolve_thing` for unit B leaves B's row unnamed, the selector skips it, and an older valid row for unit A silently supplies the scope. `PlaybookTerminalHandoff.appendSkippedSiblingToolResults` is the one producer that drops the name (§2.5). Change it to the three-argument `ChatMessage.toolResult(skipped.getId(), SKIPPED_TOOL_RESULT_JSON, skipped.getFunctionName())`. This is metadata only: handoff execution, cancellation and approval policy do not change, and the row body stays the same. The row's existing consumers are unaffected: the checkpoint evidence manifest accepts a name equal to the declared call, and the table wire and persist-stamp code do nothing with this body.
2. **Resolve and store.** Call `DocumentKnowledgeRuntime.resolveHostContextScope(this, name)`; `name` is the Thing name, and §2.1 states what the resolver needs to return a set. If a set is returned, store it with `AgentToolContext.setInjectedDocumentScope(ids, source)` and mark its **origin** as conversation. If the resolution is empty or fails, leave the turn unscoped. Log one info line with the Thing name, the document count and the resolver source (or `empty`), so a live run can tell a missing mapping from a code failure.
3. **Origin marker.** `getInjectedDocumentScopeSource()` is `custom` or `default-match` for either origin, so it cannot tell who supplied the scope. Add a turn-local origin value to `AgentToolContext`: a three-argument `setInjectedDocumentScope(ids, source, origin)` and a getter. The existing two-argument setter keeps meaning host-context, so its caller and tests do not change. Null or empty ids clear the origin along with the scope, and `AgentToolContext.clear()` clears it. No persisted field and no general scope-management API.
4. **In-turn update.** After every *executed* Java built-in `resolve_thing` dispatch in the current turn, including a result whose JSON is an error or ambiguity envelope, apply steps 1–2 to that result (a hook beside the other post-hooks; it runs on the returned JSON, not only on success). A new valid single match sets the scope when none exists and replaces a conversation-origin scope; a new result that yields no scope (ambiguous, failed, other kind, or an empty resolution) clears a conversation-origin scope and does not retain the old ids. A host-origin scope is never replaced or cleared by this hook.
5. **Default, not filter.** The defaulting in `executeSearchDocumentChunks` is unchanged: a model-supplied `documentIds` (including `[]`) suppresses the default. Only the diagnostic changes: when the applied default has conversation origin, `documentScopeSource` is `conversation-entity-resolver` instead of `host-context-resolver`. `documentScopeResolverSource` is unchanged, and a host-origin result is byte-for-byte as today.
6. **Approval continuation.** In `runParlerPostToolAgentLoop`, after `ParlerHitlContinuationContext.bindForGatedToolExecution` and before `loop.runAfterApproval`, derive a conversation-origin scope from the method's `messages` argument (the continuation's copy of `messagesCopy`) with steps 1–2. This round does **not** restore a host-origin scope on continuation. `PendingApprovalRecord` carries no host context, so the continuation cannot tell a host-context conversation apart: such a continuation stays unscoped as today unless its transcript holds a valid `resolve_thing` result, in which case it gets that conversation-origin scope. Do not add a host-context snapshot to `PendingApprovalRecord`.
7. **Failure.** Fail open: any exception leaves the turn unscoped and does not change any tool result. A history row already removed by trimming yields no derived scope; do not add a stored entity or a message-stream fallback.

Nothing new is stored: the scope is derived from the conversation's own transcript on every turn.

Cost to state in the change description: on an agent with document built-ins enabled, every turn after a successful single resolution calls the resolver once, which is an index-cache lookup plus one `ResolveDocumentSet` service invocation, and the turn start waits for it. The host-context path already pays the same cost per turn. No intent test is added to avoid it.

Consequence to state in the change description: once a scope exists, `load_topic` enforces it, so a topic from a document outside the unit's set is refused with `TOPIC_OUT_OF_SCOPE` where an unscoped conversation would have loaded it. That is the intended scoped-retrieval behaviour, and P7 covers one in-scope and one out-of-scope load. An explicit `documentIds` does not lift this: it widens the search, not the loader. R8 therefore omits `loadWith` from a topic the loader would refuse, and the way to move the scope is a new `resolve_thing`.

Consequence to state in the change description: with `toolAdmissionMode` `narrow` or `lazy`, a conversation-origin scope sets `documentScopeActive`, so the `DOCUMENTS` bucket is admitted on those turns (§2.1). That is the existing signal doing its job, and the admission policy is not edited. With `off`, nothing changes.

Risk to state in the change description: after the user switches to another unit without a new `resolve_thing`, the previous unit's scope applies until the model resolves again. Document search is read-only, a wrong scope narrows results rather than authorizing anything, and the model's explicit `documentIds` still wins for search. A topic outside the stale scope stays unloadable until the model resolves the new unit, which is what R9 tells it to do.

### R7 Topic offer lifts narrowing

Add to `AgentTaskState` a turn-local boolean `methodOffered` with a recording call and getter; it is not serialized and not part of checklist or wire state. A new hook (for example `ActiveMethodHooks.afterSearchDocumentChunks(call, result)`) runs on the Java built-in dispatch path, beside `afterLoadTopic`, on the JSON the built-in returned (before egress; a same-named extended tool never triggers it). It records the flag when the result has at least one match with `contentType` equal to `topic`. An *offer* is defined exactly so: a topic match in the built-in result. Result sampling by egress happens later, in `AgentLoop.appendCompactedExecutedToolResultToMessages`, and is deliberately not modelled: a topic that sampling removes still counts as offered. The effect is only that upstream-admitted tools stay available; an offer does not claim the model saw or loaded anything.

`DocumentTurnToolNarrowing.shouldNarrow` returns false while `methodOffered` is true, in the same position as `activeMethodPresent()`. The lift lasts for the rest of the uninterrupted turn; there is no "ignored topic" lifecycle. A page-only result leaves narrowing as before unless an earlier topic result already set the flag, so a plain document question keeps its small tool list. A topic match outside the scope, which is possible only after an explicit `documentIds`, still counts; it lifts narrowing without being loadable, which is rare and harmless.

Parsing must fail soft: a result that does not parse records nothing and changes no tool result. The hook returns immediately for any function other than `search_document_chunks`, because it runs for every built-in on that path.

Logging: `logNarrowingSkipped` runs only at iteration 1, when an offer cannot exist yet, so a reason added there would never print. Instead the hook logs one info line when the flag first becomes true in a turn. `logNarrowingSkipped` is unchanged.

Offer is **not** an active method: it does not enter `activeMethodIds`, protects no text in the budget planner, and is not carried over an approval pause. Do not persist unloaded offers. After a pause the continuation starts with fresh state and clear latches; that does not universally prevent narrowing (a sole `document_search` skill narrows at once, and a later document call can set the latch again). On the path this round serves, the model loads the topic before the approval, and round 1's carried active method supplies the preservation guarantee after resume.

Alternatives considered and not taken: (a) keep registered operational tools in every narrowed round whenever the document scope contains a topic — a larger and permanent change to a deliberate size optimisation; (b) treat any `contentType: topic` search hit as an active method — it would protect and carry text that was never loaded and conflict with round 1's definition.

### R8 A topic match says how it is used

In `buildSearchMatch`, when the chunk's `contentType` is `topic` and the loader would not refuse its document for scope, add `"loadWith": "load_topic"` after `contentType`. The scope test is the one `executeLoadTopic` applies (no injected scope, or the injected ids contain `docId`); extract it to one private helper used by both, so they cannot drift. No other match gets the field, no field is removed or reordered, and `get_document_chunk` is unchanged.

No registry test is needed: the Java search and the Java loader are registered together (§2.3), so `loadWith` can only be produced where the loader exists. `buildSearchMatch` has no registry to ask, and this avoids adding a seam for a case that cannot occur.

The tool description of `search_document_chunks` gets one sentence, with this meaning: "A match with loadWith is a method: load it with that tool, because its text is not in the snippet."

### R9 Routing guide: search the unit's documents first

In `llm_tool_routing_guide.txt`, "Document knowledge" section, directly after the round-1 line, add one general sentence with this meaning: "When the user asks what to collect or do about a symptom on a named unit, use the unit already resolved in the conversation, call resolve_thing only when the unit is not yet established or has changed, then search that unit's documents before calling operational tools." The default scope applies to that search, so the sentence does not tell the model to pass `documentIds`. It must not read as a mandatory new `resolve_thing` call on every symptom turn: that call sets the non-document latch, switches narrowing off, and would hide whether R6 and R7 work. The round-1 sentence about `load_topic` stays. `DocumentKnowledgeRoutingGuideTest` asserts existing phrases: add, do not alter. Per `docs/agent/LLM_CONTEXT.md` this is routing guidance; call semantics stay in the tool descriptions. No feature flag or conditional prompt mechanism is added in this round.

### R10 Features

Add two names to `RuntimeFeatures`, in this order after the round-1 names: `entity-document-scope/1` (R6) and `topic-offer/1` (R7 and R8). Both are listed exactly when the Java document built-ins are registered. That is the same fact as the existing `names(boolean javaTopicLoaderRegistered)` argument (§2.3), so the signature stays. With the loader the value is `["topic-load/1","active-method-tools/1","entity-document-scope/1","topic-offer/1"]`; without it, `["active-method-tools/1"]`. `entity-document-scope/1` reports that the runtime derives the scope, not that a given deployment's resolver returns a set (§2.1). Unchanged: always-present top-level array, deterministic order, no dependence on an active turn.

## 8 Decisions proposed for reviewer agreement, and what is deferred

- Scope from the newest single `resolve_thing` result in the history, recomputed per turn; no stored entity. Alternative: a stored conversation entity. Rejected for now: more state, and the history already carries the fact.
- Every row for an unexecuted call carries its tool name, corrected at the one producer that drops it. Alternative: select by pairing assistant tool calls with rows by id, which needs no producer edit. Not taken: the selector would differ from the existing `executedToolName` consumers, and the producer fix also leaves the transcript more accurate.
- Offer lifts narrowing; it neither protects text nor survives a pause.
- `loadWith` is an additive field on topic matches only, and only where the loader would not refuse the document for scope.
- A conversation-origin scope reports its own `documentScopeSource` value instead of reusing the host-context label. Alternative: keep one label. Rejected: the result would claim a host context that does not exist, and the live check reads this field.
- `load_topic` enforces a conversation-origin scope as it does a host-origin one. Alternative: enforce host origin only, since a conversation scope is weaker and can be stale. Not taken: it changes round 1's rule, and R9 gives the recovery path (`resolve_thing`). Reopen if live runs show a correct topic refused because of a stale scope.
- **Deferred, with the evidence that would reopen it:** a topic lane in ranking (reserved slots for the best topic matches regardless of document rank), and a turn-start topic probe that offers matching topics without a model search. Reopen the first if a **scoped** search over the intended document set fails to return a relevant topic among the top hits in repeated runs; reopen the second if, with R6–R9 in place, the model still does not search in a meaningful share of runs of the failing conversation. Unscoped ranking is not a reason to reopen either: scoped retrieval is the premise.
- The source-link citation, model choice to load, and answer wording remain model behaviour.

## 9 Glossary

- **entity scope** — the document ids resolved for the unit named in the conversation, used as the default `documentIds` of a search.
- **topic offer** — a search result that contains a `contentType: "topic"` match; turn-local, weaker than an active method.
- **active method** — as in round 1: a loaded topic or non-document skill.
- **narrowing** — as in round 1: `DocumentTurnToolNarrowing`.
